# Fuzz targets

Every parser of untrusted input gets a fuzz target that feeds it random and mutated input to find crashes and hangs (ADR-0006 §5, ADR-0025 §4). Today the targets cover bayan-opc's package layer (ZIP, part names, content types, relationships, core properties, compound files), bayan-xml, the Fidelity Lab's PDF extractor, hint reader and document scanner, the engine's protocol messages, tile requests, configuration and recordings, and CRDT updates from other people; a work package that adds a parser, of fonts or images for example, adds its target. The targets live here, and CI runs them on every pull request that can affect them and every night (see [In CI](#in-ci)).

## Running them

The targets use [cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz), which needs a nightly Rust toolchain, so this folder is a separate Cargo workspace, excluded from the main one in the root `Cargo.toml`. Use the nightly version and the cargo-fuzz version pinned in the docs repository's `scripts/cloud-environment-setup.sh` (`RUST_NIGHTLY`, today `nightly-2026-10-02`, and cargo-fuzz 0.13.2), which CI uses too; BayanDocs cloud sessions have both. From the repository's root:

```sh
cargo +nightly-2026-10-02 fuzz build --target x86_64-unknown-linux-gnu
cargo +nightly-2026-10-02 fuzz run --target x86_64-unknown-linux-gnu zip_archive fuzz/corpus/zip_archive -- -max_total_time=600 -dict=fuzz/dictionaries/zip.dict -rss_limit_mb=2048 -timeout=10
```

`--target` names the host explicitly because cargo-fuzz's release build is statically linked (musl) and would otherwise build for its own target. Use `-dict=fuzz/dictionaries/xml.dict` for bayan-opc's targets that read XML, and `-dict=fuzz/dictionaries/ooxml.dict` (WordprocessingML and Markup Compatibility) for bayan-xml's. To run the targets the way CI does, with its seeds, settings and summary, use `ci.py` (Python 3.11 or later, standard library only) after building them:

```sh
python3 -I fuzz/ci.py seeds fuzz/seeds
python3 -I fuzz/ci.py run --all --seconds 150 --seeds fuzz/seeds
python3 -I fuzz/ci.py minimize --all
```

`run` also takes target names instead of `--all`, and `--jobs` for how many targets run at the same time (default 4). The corpora go to `fuzz/corpus/<target>/`, where `cargo fuzz run` finds them too, the inputs that fail to `fuzz/artifacts/<target>/`, and each target's output to `fuzz/logs/`. The seeds, corpora, crash artifacts, logs and build output stay local (`.gitignore`).

The targets of the engine and of CRDT updates (CORE-010) keep their code in a library of this workspace, `src/` (`bayan_fuzz`), whose tests run their checks without a fuzzing engine. CI runs them before fuzzing; run them after changing `src/`:

```sh
cargo +nightly-2026-10-02 test --locked --manifest-path fuzz/Cargo.toml --lib
```

## In CI

`.github/workflows/fuzz.yml` first runs the supply-chain checks on this workspace's `Cargo.lock` (see Rules), then builds every target with AddressSanitizer and runs them with `ci.py`, which holds each target's settings in `TARGETS` and refuses to run when a target of `Cargo.toml` has none, so that no target is left out:

- **Pull requests** that change bayan-opc, bayan-xml, bayan-engine, bayan-crdt, bayan-lab, bayan-lab-layout, bayan-lab-compare, this folder, the root `Cargo.toml`, `.cargo/` or the workflow: the tests of the targets' harness run, then every target that is not parked for 150 seconds (the default-limits targets 300), four at a time, from the seeds and from the corpus that the last nightly run saved. A pull request only reads that corpus and never saves one. Starting from it, rather than from the seeds alone, replays every input that the nightly runs have found, and gives `compound_file`, which has no seed, a corpus to start from: from nothing, it reached 56 edges of coverage in 20 seconds and 533 in 4 minutes, where CORE-005's seeded runs reached 1,606. The job takes about 25 minutes: building the targets takes about four minutes since Loro is built with AddressSanitizer, and the tests of the harness about two. It is not a required check, because a path filter skips it on most pull requests; look at it before merging a pull request that touches a parser.
- **What the shared corpus means for pull requests**: an input in the nightly corpus passed when it was saved. If a later change on `main` makes it crash, every pull request that touches the fuzzed crates fails on it, as the nightly run does, until the change is fixed; any crash is a release blocker (ADR-0025 §4). Nothing that a failing run found is saved: a run in which a target failed saves no corpus at all (see the next item), and libFuzzer keeps the input that failed apart, in `artifacts/` on the runner, which no step uploads. A pull request therefore fails on a crash that a nightly run found only if its own fuzzing finds that crash again, while the next nightly runs, which start from the same corpus, are likely to find it again until it is fixed; until then the corpus does not grow.
- **Every night** (02:23 UTC), and on demand (Actions → Fuzzing → Run workflow): every target runs for 15 minutes (the default-limits targets 30) from the corpus that the previous run left. If every target passed, each corpus is then minimized (libFuzzer's `-merge=1` keeps only the inputs its coverage needs) and saved with actions/cache for the next run, so the corpora grow from run to run without keeping inputs they do not need. A run in which a target failed, or minimizing failed, saves no corpus: the workflows of pull requests can read the cache, and the corpus of a target that ran out of memory can hold the input that used the memory, because libFuzzer checks the peak memory only once a second and blames the input that is running at that moment, while the one that used the memory may have finished and been added to the corpus. Only these runs save a corpus, into the cache of the branch they ran on: scheduled runs on `main`, and manual runs on the branch they were started on. A run reads the latest corpus of its own branch, or else of `main`, and a pull request that of its base branch or of `main`, so a pull request against `main` reads only what runs on `main` saved. The first run on a branch starts from the seeds alone if `main` has no corpus yet.
- **Failures**: a crash (a panic included), a timeout, running out of memory or a leak fails the job. Of a target that failed, the job log, an annotation on the run's page and the job summary name only the target and the kind of failure, and nothing else about it is public (see [When a run fails](#when-a-run-fails)). The job summary lists every other target's result, how long it ran, its executions, coverage (edges and features), corpus and peak memory, and, after a nightly or manual run in which every target passed (the only runs that minimize the corpora), the coverage of each minimized corpus. That coverage leaves out what only the seeds reach: libFuzzer never copies the seeds into the corpus, and every run reads them again.
- **Notifications**: GitHub notifies whoever last changed the workflow's cron schedule when a scheduled run fails. Agents push and merge under the owner's account, so that is the owner, by email and on github.com as the owner's notification settings for Actions say (Settings → Notifications → Actions). GitHub switches scheduled workflows off after 60 days without activity in the repository; whoever switches one on again receives its notifications from then on.

### Parked targets

A target that a known problem makes fail every run is parked: its entry in `TARGETS` of `ci.py` gives the reason (`parked`). The automatic runs (`ci.py run --all` and `minimize --all`, in pull requests and at night) leave it out and list it in the job summary as `parked`, never as passed, while CI still builds it with the others and runs the tests of its harness, so it cannot stop compiling or lose its checks unnoticed. `ci.py run <target>` still fuzzes it by hand. `test_ci.py` fails if any target but `crdt_import` is parked, or a parked target has no reason.

`crdt_import` is parked: a problem reported privately in another project's code keeps it out of the automatic runs until a release of that project fixes it. The monthly dependency session runs it by hand on each new version of Loro, after building the targets and writing the seeds as above (`python3 -I fuzz/ci.py run crdt_import --seconds 1800 --seeds fuzz/seeds`), and once it passes, un-parks it by removing its `parked` reason, in the pull request that brings that version. Until then, the import path of CRDT updates is fuzzed by hand only (ADR-0008, decision 4). A failure that such a run finds is handled like every other (see [When a run fails](#when-a-run-fails)). That run is a single process, unlike CORE-010's 30-minute run in libFuzzer's fork mode, which restarts it, and it keeps every document that a contained panic of Loro's poisoned (`src/crdt.rs`), so its memory grows with every such panic: compare its peak memory, which `ci.py` reports, with `-rss_limit_mb` (2,048 MB) before reading an out-of-memory failure there as Loro's.

**The time budget.** `ci.py` runs four targets at a time, the longest first. The eighteen targets, the parked one counted because it comes back, have 20 shares of `FUZZ_SECONDS` (the two default-limits targets 2 each, the sixteen others 1 each), and five rounds of four hold 20, so every target has run after five rounds: 12.5 minutes on a pull request, 75 minutes at night. CORE-010's five targets added the fifth round (LAB-003's follow-up 9), and with it the job's timeouts went from 30 to 40 minutes on a pull request and from 90 to 120 at night, which also leave room for the longer build and the tests of the harness. CORE-011's `lab_scan` took the last share they held, so the next target needs a sixth round. `test_ci.py` counts the rounds as `ci.py` schedules them (`rounds`) and fails when `FUZZ_SECONDS`' comment in `.github/workflows/fuzz.yml` states another number or when a timeout no longer leaves every target its full time, so such a target changes the comment, the timeouts and this paragraph together.

Every target may take 2,048 MiB (`-rss_limit_mb`), as in the runs of CORE-005 and CORE-006; the next section explains why that suits the default-limits targets too.

The seeds come only from public, licensed files of this repository, written by `ci.py seeds`: never add documents of the private corpus, because the corpora that grow from the seeds are saved in the Actions cache, which the workflows of pull requests can read.

Without `-len_control=0`, libFuzzer lengthens its inputs slowly, starting from the longest input of the corpus: in a ten-minute trial the default-limits targets made no input longer than 39 KB, although they may make inputs of 1 MiB. With it, they passed 64 KB within four minutes, and the nightly corpus keeps the longer inputs that reach new code.

The default-limits targets get a longer timeout because an input that fills bayan-opc's default metadata budgets takes seconds under AddressSanitizer: the worst metadata of the memory measurements below took 12 s in `package_default_limits`, which reads such a package twice (and the 34 MB combination 24 s, but its entry list alone needs 10 MB of ZIP headers, more than an input can hold). A 1 MiB input can hold metadata like the former, since bayan-opc lets a part compress up to 100 to 1. 60 s is five times that, while work that grows faster than its input takes minutes.

### The engine's targets and `crdt_import`

Their harness is the library in `src/` (`bayan_fuzz`): `src/engine.rs` for the four engine targets, `src/crdt.rs` and `src/loro_panics.rs` for `crdt_import`, and `src/tests.rs` for the tests that need a process of their own. The files in `fuzz_targets/` only call it.

- **A caught panic still fails an engine target.** The engine catches the panics of its handlers and of rendering and reports them (engine protocol §12), but libfuzzer-sys's panic hook (`initialize` in its `src/lib.rs`) aborts the process on every panic before anything can catch it, so the run fails with `crash`; bayan-ffi's silent hook is not linked into these targets. The harness also refuses the error `panic` and `engine.error` with `recoverable: false` in the engine's answers, which would show a caught panic even without that hook. The tests in `src/tests.rs` show both, with an engine whose test switch lets `diag.panic` panic; the targets themselves run with the test switches off.
- **Work per input.** The engine's limits allow requests that take long by design: a tile of 4,096 × 4,096 pixels takes about a third of a second natively and more under AddressSanitizer, and one replay may render 2³⁰ pixels, about 20 seconds natively (engine protocol §13). So each engine harness renders at most 2²² pixels per input (`PIXEL_BUDGET`), its own tiles included: the last tile of `engine_messages`, and the replay of a recorded call and the reference tile of `engine_tile`. It reads each message, and each entry of a recording, before the engine does, counts the pixels it asks for, and leaves out a message, or the whole input, that would exceed the budget. It reads them as the engine does, only more leniently, so that it never counts less than the engine renders: with typed structures that skip every field they do not need with serde's `IgnoredAny`, which serde_json skips at any depth, as the engine skips the fields it does not know (a `serde_json::Value` refuses nesting deeper than 128 levels); with invalid UTF-8 replaced; with both the size and the message of a recording's entry counted, whatever its kind; and with a recording, or an entry, written as a JSON array, which serde's derived readers also accept, by position, counted as over the budget. `engine_messages` also hands at most 64 messages of an input to the engine (`MAX_MESSAGES`): the accessibility tree of the whole mock document, about 180 KB of JSON, takes about 30 ms under AddressSanitizer to answer and check. libFuzzer's timeout then catches work that grows faster than its input rather than work the limits allow. Inputs are at most 64 KiB, as for the other targets. They reach the limits of documents, text, compositions, tiles and coordinates, but not three of the engine protocol's §13 limits, which the engine's own tests cover: 100,000 entries in a recording, which a 64 KiB input cannot hold; 2³⁰ pixels in one replay, far above the budget; and 1,024 blobs in the engine's store, which `engine_messages` cannot fill because the harness releases every blob the engine creates (a recording that lists more than 1,024 blobs, a plain count, is within `engine_replay`'s reach). The 16 MiB and 64 MiB limits are plain length checks, which the engine's tests reach too. Nothing renders a full tile of 4,096 × 4,096 pixels, neither the targets nor the engine's tests, though both reach 4,096 pixels on one side. The budgets bound only the pixels that an input makes the engine render, and the messages that `engine_messages` hands to it: every other kind of work that an entry of a recording causes is bounded only by the input's size. `engine_messages` runs about 70 inputs a second, because each input starts an engine and every answer is checked against the JSON Schema, which takes about 40 % of the time; the other three run hundreds to tens of thousands a second.
- **Loro's panics.** `crdt_import`'s `init` replaces libfuzzer-sys's hook with one that lets a panic unwind only when it is Loro's, so that `Doc::import` can contain it, and hands every other panic to libfuzzer-sys's hook, which aborts. A panic is Loro's when, counting outward from the frame that raised it, the first frame outside the standard library belongs to `loro` or to a package that only Loro brings into `Cargo.lock` (such as `loro-internal` or `generic-btree`; not `serde`, `memchr` or other packages that BayanDocs' crates use too), as the target's debug information names the frame's file (`…/registry/src/<index>/<name>-<version>/…`). The target computes that set from this `Cargo.lock`, compiled into it, so it follows every dependency change by itself. Whatever it cannot read for certain counts as not Loro's and fails the run: a frame without a file where the decision falls (cargo-fuzz's release builds keep the debug information, `[optimized + debuginfo]`), a file in no package of the lockfile, or a lockfile in another layout, which stops the target before it fuzzes. The hook prints nothing for Loro's panics and counts them; for any other panic it writes why it is not Loro's and the whole backtrace into the target's log, which stays private like every log (see [When a run fails](#when-a-run-fails)).
- **Poisoned documents are kept.** bayan-crdt never frees a document after a contained panic, because freeing it can panic again (`Doc`'s `Drop`). `crdt_import` keeps every poisoned document, its handles and its undo manager for the rest of the process, so that LeakSanitizer finds them reachable rather than leaked; each takes some tens of kilobytes.
- **The seeds of `crdt_import`.** Only Loro writes its blobs, so `ci.py` writes none. The target edits six documents itself (text in several scripts, atoms, marks of the document model's families, stories, registries with property maps and movable lists, undo and redo), loads each as a second replica, edits both concurrently, and keeps the updates, the whole history, the merged snapshot and a shallow snapshot, with CORE-004's base document and its two updates from `crates/bayan-crdt/tests/fixtures/`. Its custom mutator starts from them and applies the CORE-004 spike's structure-aware mutations, ported from `spikes/crdt-model/src/fuzz.rs`, and now and then libFuzzer's own, then gives nine blobs in ten the checksum that Loro checks.

### The memory limit of the default-limits targets

bayan-opc documents a memory bound: with the default limits, opening a package and reading its core properties take at most about 256 MiB (`crates/bayan-opc/src/lib.rs`, "Limits"; derived from two measured worst cases, 73 MiB of entries and 123 MiB of metadata). The limit must let a package that needs that much pass, AddressSanitizer's overhead included, and fail the run when an input needs far more. These are the worst packages of that bound's derivation, built with the generators of CORE-005's pull request and, since CORE-011 changed how bayan-opc reads its metadata, with those of CORE-011's review, measured with the code of CORE-011:

| Package | Opened, with its core properties, natively | The same under AddressSanitizer | `package_default_limits` under AddressSanitizer |
|---|---|---|---|
| The worst metadata: a content types stream of 8 MiB with long CJK part names in UTF-16, then a relationships part with long CJK identifiers in UTF-16 that fills both budgets (16 MB, stored) | 123 MiB | 282 MiB | 663 MiB |
| The worst with the core properties: the same stream, then the core properties part as the last part, one long CJK run in UTF-16 with a character reference in it (16 MB) | 122 MiB | 261 MiB | 488 MiB |
| The worst list of entries: 9,999 relationships parts with CJK names of about 1 KiB whose source parts do not exist (22 MB) | 73 MiB | 355 MiB | 758 MiB |
| The worst combination found: those entries, then the worst metadata (38 MB) | 182 MiB | 574 MiB | 1,211 MiB |
| The same, with the core properties part holding the metadata | 182 MiB | 556 MiB | 1,044 MiB |
| CORE-005's worst combination, whose metadata was the worst while bayan-opc parsed it into a tree (34 MB) | 166 MiB | 506 MiB | 935 MiB |
| A one-byte input (libFuzzer alone) | | 33 MiB | 34 MiB |

The figures are the peak resident memory added by opening (native column, in a release build, the larger of the peaks on the main thread and on a thread of its own, as `crates/bayan-opc/src/lib.rs` measures them) or of the whole process, the package's own bytes included (the other two columns). The middle column used a scratch target that only opens the package with the default limits and reads its core properties; the last is the target as CI builds it, run on the worst combination with its long relationships in a part's relationships part instead of the package's, which takes as much memory but not hours: the target resolves every relationship of the package once for every part. AddressSanitizer takes 2 to 5 times the native memory (a guard zone around every allocation, freed memory kept back for a while to catch late uses, and its shadow memory), the most for the entry list's many small allocations. `package_default_limits` takes more again, because it also reads every part, writes the package again and opens the copy while the original is still open. 2,048 MiB leaves about two fifths of it free above the worst of these packages, for libFuzzer's corpus and AddressSanitizer's quarantine, while an input that needs about three times the documented bound to be opened once, or about one and a half times for each of the target's two openings, exceeds it and fails the run as out of memory. `zip_archive_default_limits` reads every entry into memory instead, which the archive's compression ratio limits to 100 times the input: its peak on the same packages was 601 MiB. (Each figure in the table is the most of three runs, which varied by a few MiB at most.)

### When a run fails

What a run finds stays private, because it can disclose a vulnerability. libFuzzer writes the input that failed into the target's log (in hex, as text and in Base64, if it has at most 256 bytes), next to the panic message or the sanitizer's report and the stack trace, and an input that mutation made fail is a working proof of concept. Most targets also run other projects' code, such as miniz_oxide's, quick-xml's, serde_json's and Loro's, so a failure can be an undisclosed vulnerability in their released software, which `SECURITY.md` asks everyone to keep private. CI therefore uploads no input that failed and prints no target's log, not even a passing one's, since libFuzzer also writes an input that ran slowly into it: `ci.py` shows only the name of each target that failed and the kind of failure, and the inputs and logs stay on the runner, which GitHub deletes after the job.

1. Open the failed run (Actions → Fuzzing, or the link in GitHub's notification). Its summary, and an annotation for each, names every target that failed and the kind of failure: `crash` (a panic included), `timeout`, `out of memory` or `leak`. Rarely it says instead that libFuzzer exited with a code and kept no input (a negative code is the signal that stopped it, such as -9 when the system stopped it for lack of memory), or, when the corpora were minimized, that merging reported a failure or printed no summary.
2. Reproduce the failure privately, on your own computer or in a BayanDocs cloud session, never in a workflow: on the commit that the run tested, build the targets, write the seeds and run the target that failed from them with `ci.py`, which uses CI's settings. Fuzzing is random, so finding the failure again can take longer than the run that found it, above all when a nightly run found it from its corpus, which stays in the Actions cache: run the target longer, or again.

   ```sh
   git checkout <commit>
   cargo +nightly-2026-10-02 fuzz build --target x86_64-unknown-linux-gnu
   python3 -I fuzz/ci.py seeds fuzz/seeds
   python3 -I fuzz/ci.py run package_default_limits --seconds 1800 --seeds fuzz/seeds
   ```

   When the target fails, `ci.py` says where its log is (`fuzz/logs/<target>.log`, with the panic message and its stack trace, or libFuzzer's report of a timeout, of running out of memory or of a leak) and where the input that failed is (`fuzz/artifacts/<target>/`, named by what went wrong and by its SHA-1: `crash-…`, `timeout-…`, `oom-…` or `leak-…`). Run the target on that input alone, with the target's options from the settings above for a timeout or out of memory, and let `cargo fuzz tmin` shrink it to the smallest input that still fails. An `oom-…` input may not be the one that used the memory: libFuzzer checks the peak memory only once a second and blames the input that is running at that moment, so if the kept input alone stays within the limit, find the failure again by running the target, as above:

   ```sh
   cargo +nightly-2026-10-02 fuzz run --target x86_64-unknown-linux-gnu package_default_limits fuzz/artifacts/package_default_limits/crash-<sha1> -- -rss_limit_mb=2048 -timeout=60
   cargo +nightly-2026-10-02 fuzz tmin --target x86_64-unknown-linux-gnu package_default_limits fuzz/artifacts/package_default_limits/crash-<sha1>
   ```

   For `crdt_import`, the log also says why the panic was not Loro's (for example `raised in /…/crates/bayan-crdt/src/import.rs`), with the whole backtrace; an abort or running out of memory has the sanitizer's report instead. The input's first byte chooses the preset and the base document (`src/crdt.rs`). Whose code failed decides who reports it: the first frame outside the standard library, counting outward from the one that raised the panic or made the allocation, is BayanDocs' or another project's.

3. Report it privately, as `SECURITY.md` says: any crash, hang or runaway memory that a document could cause in BayanDocs is a security problem. Never put the input, the log or a description of the problem into an issue, a pull request, a commit message or a workflow's output; an agent tells its orchestrator or the owner privately, and its pull request says only that a report was made. If the failure is in another project's code, the owner reports it privately to that project's maintainers, as that project's security policy asks. Any crash is a release blocker (ADR-0025 §4).
4. Fix it in a pull request of its own, with a regression test in the crate it affects (see Rules), once the handling of the report lets the problem become public: a pull request is public too.

## Rules

- **The harness of the engine's and the CRDT's targets is tested.** Its library in `src/` has tests (`cargo +nightly-2026-10-02 test --locked --manifest-path fuzz/Cargo.toml --lib`), which the fuzzing workflow runs before it fuzzes; a change to `src/` keeps them passing. The JSON Schema validator it uses is the engine tests' own file (`crates/bayan-engine/tests/engine/support/schema_validator.rs`), compiled by its path.

- Its `Cargo.lock` is committed, and its dependencies follow the same rules as the main workspace: exact pins, at least 24 hours old, licenses on the allowlist (ADR-0017). Resolve it with the pinned nightly, which enforces the 24-hour minimum age (`cargo +nightly-2026-10-02 update` in this folder), and give every package that the main `Cargo.lock` also has that lockfile's version (`cargo +nightly-2026-10-02 update -p <package>@<new> --precise <main's>`), because a fresh resolution picks newer ones. CI builds the targets from it with `cargo fetch --locked` and fails if building would change it.
- **License check:** `cargo xtask verify` checks this workspace's dependencies with cargo-deny against its own `deny.toml`: the main policy plus one exception, the NCSA license of libFuzzer that libfuzzer-sys bundles, which ADR-0017's amendment of 2026-10-08 accepts for fuzzing dependencies that never ship. The exception is for that one crate and never goes into the main workspace's `deny.toml` (an xtask test keeps it so).
- **Exact pins and age check:** `cargo xtask check-exact-pins` and `cargo xtask check-lockfile-age`, the first step of `cargo xtask verify`, of the CodeQL workflow's Rust job and of the fuzzing workflow, read this workspace like the main one (bayan-core#22). Every dependency of the targets is pinned exactly, and every package version that a change adds to this `Cargo.lock`, compared with this file at the merge base, must have been published on crates.io at least 24 hours before the commit that added it, with the checksum crates.io published. This workspace may depend by path on members of the main workspace, such as bayan-opc and bayan-xml, whose own dependencies are checked with the main workspace, and on nothing else outside this folder; their dependencies' versions in this `Cargo.lock` are checked with it. No hand check is needed any more.
- **Every target runs in CI:** a new target needs its settings in `TARGETS` of `ci.py`; the fuzzing workflow fails until it has them (`test_ci.py` checks it, and `ci.py run --all` refuses to run without them). `zip_archive_default_limits` and `package_default_limits` are copies of `zip_archive` and `package` that differ only in their limits and description (compare them with `diff`): change each pair together.
- **The package targets read their written copy back with raised limits**, because `PackageWriter` does not apply the reader's limits (its documentation in `crates/bayan-opc/src/package.rs`): each limit that writing a package unchanged can exceed is raised by exactly what the writer can add, which the comment at that reading derives. BayanDocs/bayan-core#27 makes the writer keep within the reader's limits; it then reads the copy back with the original limits again.
- Record how long each target ran, and on which commit, in the pull request that adds or changes it. An input that found a bug becomes a regression test in the crate it affects.
- libfuzzer-sys compiles LLVM's libFuzzer (C++) in its build script. That is acceptable here because nothing in this workspace is linked into, or shipped with, BayanDocs; the parsers under test stay pure Rust (ADR-0006).
