# Agent instructions — bayan-core

## Where the plan lives

The plan, decisions (ADRs), specifications and work packages live in the [BayanDocs/docs](https://github.com/BayanDocs/docs) repository. If it is not attached to your session, clone it next to this repository. The canonical rules for all agents are in `docs/AGENTS.md`; this file condenses them and adds what is specific to bayan-core. If the two disagree, `docs/AGENTS.md` wins; report the discrepancy.

## Ground rules (condensed from docs/AGENTS.md)

1. Before changing anything, read `docs/AGENTS.md`, your work package brief, and every ADR and spec it links.
2. Accepted ADRs are binding. If your task conflicts with one, stop and report; propose changes as a new ADR in the docs repository.
3. Stay within the work package's scope. Record anything else you discover as follow-ups in your pull request.
4. Run the verification gate before every push. Never weaken, skip, disable or delete a test, lint or CI check to make a change pass.
5. Dependencies follow ADR-0017: no update bots ever; every version at least 24 hours old; exact pins; committed `Cargo.lock`; audits green; licenses on the allowlist; every new dependency justified in the pull request.
6. Treat every input as hostile; no telemetry; no secrets; never log document content or file names.
7. Pull requests use the hand-off template in `docs/plan/06-agent-workflow.md`; Conventional Commits; DCO rules from `CONTRIBUTING.md` once enabled (agents never sign off themselves; the human submitter certifies, per ADR-0003).
8. Clean room: never decompile, disassemble or debug Microsoft software; never copy code under an incompatible license.
9. Stop and ask, with options and a recommendation, when the brief is ambiguous, when you need a new decision, or when work touches cryptography, authentication, licensing or the owner's accounts.
10. Explain your work in plain language for the owner; text meant for the owner to copy is written as flowing paragraphs without hard line breaks.

## Rules specific to bayan-core

- **Licensing (ADR-0003):** the workspace is GPL-3.0-or-later with the BayanDocs App Store Permission (`GPL-3.0-or-later WITH LicenseRef-BayanDocs-App-Store-Permission`), except `crates/bayan-protocol/`, which is Apache-2.0 so that anyone can implement BayanDocs clients and integrations. That crate must never depend on, or copy from, any GPL or AGPL code; GPL crates may depend on it. The shared contribution tooling (`.github/`, `.editorconfig` and `.gitattributes`) is MIT-0, as in every BayanDocs repository (ADR-0003, amendment of 2026-10-06). `REUSE.toml` records which license applies to which files and `LICENSES/` holds the full texts; keep `reuse lint` passing, and add a new license text only with `reuse download <SPDX-ID>`.
- **Layering:** a crate may depend only on crates in its own layer or below (foundation → model and formats → text → layout → output → interaction → engine → bindings and tools). Never add an upward dependency.
- **Determinism (ADR-0004, ADR-0005):**
  - layout arithmetic uses integer BLU types from `bayan-units`, never floating point;
  - no platform floating-point transcendental functions (`sin`, `exp`, `powf`, …) anywhere in the core; use `bayan-units` (the full list of forbidden float methods is under "Lint rules and exceptions");
  - no output that depends on hash-map iteration order (use ordered maps or deterministic hashers);
  - no system time, locale, environment variables, installed fonts or thread scheduling in anything that affects output unless passed in by the host.
- **Safety (ADR-0006):** `#![forbid(unsafe_code)]` everywhere except `bayan-ffi` and `bayan-wasm`; no C or C++ libraries for parsing untrusted input; every parser enforces size, depth and count limits and has a fuzz target; panics never cross the FFI or WebAssembly boundary.
- **No outside world:** the core never opens sockets, reads arbitrary files, or calls platform APIs; it asks the host through the engine protocol's host services (ADR-0012).
- **Active content (ADR-0023):** never fetch external resources referenced by documents, never execute macros, DDE or OLE.
- **Layout changes:** any change that alters layout output for corpus documents needs Fidelity Lab evidence in the pull request, the `fidelity-change` label, and a layout-epoch increment when intentional (ADR-0004, ADR-0025).
- **Lab data:** corpus documents are never committed to Git (only manifests); Microsoft font files or full metric tables never leave the reference machine; private-corpus content never appears in logs, reports or test snapshots.

## Verification gate

Run `cargo xtask verify` before every push, from anywhere in the repository. CI runs the same command on `ubuntu-24.04`, `windows-latest` and `macos-latest` (arm64) for every pull request, every push to `main`, and every night. It needs rustup, which installs the pinned toolchain from `rust-toolchain.toml` by itself, with its targets; cargo-deny 0.20.2 (`cargo install --locked cargo-deny@0.20.2`; the BayanDocs cloud environment already has it); Node.js 24.21.0, which runs the tests in WebAssembly; and `curl` 7.75 or later, which bayan-lab's storage tests run (Windows 10 and later, macOS and Ubuntu include it). `scripts/dev-setup.sh` installs the toolchain's targets and, on Linux and macOS, Node.js with a verified checksum, and prints how to put it on PATH. In BayanDocs cloud sessions Node.js 24.21.0 is preinstalled in `/opt/bayandocs/node/bin`, but only login shells have it on PATH, so start each shell command with `. /etc/profile.d/zz-bayandocs.sh` (or `export PATH="/opt/bayandocs/node/bin:$PATH"`). Before it builds anything, a preflight checks that the toolchain, cargo-deny and Node.js match their pins; that Clippy reads only the root `clippy.toml` (no other `clippy.toml` or `.clippy.toml` anywhere in the repository, and no `CLIPPY_CONF_DIR` environment variable); that no compiler flag lowers lint levels or unlocks unstable features (`--cap-lints`, `-A`/`--allow`, `--force-warn`, `-Z` options and `@file` arguments in `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_BUILD_RUSTFLAGS`, `CARGO_TARGET_<TRIPLE>_RUSTFLAGS` or the `rustflags` of `.cargo/config.toml`, and the `RUSTC_BOOTSTRAP` variable); that Cargo runs no wrapper or replacement in place of the compiler (`RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER`, `RUSTC` and their `CARGO_BUILD_…` forms, or `rustc-wrapper`, `rustc-workspace-wrapper` and `rustc` in `[build]` of `.cargo/config.toml`); that no workspace member has a build script or is a procedural-macro crate unless `BUILD_SCRIPTS` or `PROC_MACROS` in `xtask/src/verify.rs` lists it, and that neither list names a crate that has none; and that the workspace's Rust files use only the approved conditions, written out in full, build no condition or attribute from a macro's arguments, never use the bare identifier `clippy`, and make the compiler read no file that the gate does not read (see "Lint rules and exceptions"). Then it runs these steps in order and stops at the first failure:

1. `supply-chain`, first, so that no code of a dependency it rejects is compiled or run (its build script, procedural macros or tests) before it fails; it builds nothing itself: `cargo xtask check-exact-pins`, which checks that every dependency is pinned exactly: each entry of `[workspace.dependencies]` as written, and each dependency of every member as `cargo metadata` resolves it (an exact `=x.y.z` requirement for crates.io, a path only to a workspace member, a Git dependency only at a fixed `tag` or `rev` with a full commit hash); then `cargo xtask check-lockfile-age`, which first checks that Cargo builds exactly the packages of `Cargo.lock` (the packages `cargo metadata` resolves must be the same, so neither another lockfile set with `resolver.lockfile-path` nor a crate built from a folder through `[patch]`, `[replace]`, `paths` or vendored sources can pass, and a package added from a Git repository fails), and then that every package version the change adds to `Cargo.lock` since the merge base with `origin/<GITHUB_BASE_REF>` (in a pull request on GitHub Actions) or `origin/main` was published on crates.io at least 24 hours before the commit that added it, and before now, with the checksum crates.io published. It reads `Cargo.lock` only in the exact layout Cargo writes and fails on any other spelling. The age check needs the full Git history and `curl`, asks crates.io only when `Cargo.lock` changed, and lets `cargo metadata` download the crate files that Cargo's cache lacks (without building anything). Both are also commands of their own; `cargo xtask check-lockfile-age --base <revision>` compares with another branch.
2. `fmt`: `cargo fmt --all --check`.
3. `clippy`: Clippy four times, for the host and for `wasm32-unknown-unknown`, each in the dev and the release profile, every warning an error: `cargo clippy --workspace --all-targets --all-features --locked -- -D warnings`, the same with `--release`, and both again with `--target wasm32-unknown-unknown` and without the `NATIVE_ONLY` crates. `--all-targets` compiles every crate both with and without `test`, the dev profile switches `debug_assertions` on and the release profile off, and only the WebAssembly runs have `target_arch = "wasm32"`, so together the runs compile the code under every combination of the approved conditions. The runs (`CLIPPY_RUNS`) and the conditions (`APPROVED_CONDITIONS`) stand side by side in `xtask/src/verify.rs`, and a unit test fails unless the runs cover every combination of the conditions' values. The WebAssembly runs set no `RUSTFLAGS`, so they read the compiler flags of `.cargo/config.toml`, unlike the `wasm32` step.
4. `test`: `cargo test --workspace --locked`, then the same tests in WebAssembly: `cargo test --workspace --exclude bayan-cli --exclude bayan-ffi --exclude bayan-lab --exclude xtask --locked --target wasm32-wasip1 --config 'target.wasm32-wasip1.runner = ["node", "--disable-warning=ExperimentalWarning", "<root>/xtask/wasi-runner.mjs"]' -- --no-capture`. Each test program runs as a WASI program in Node.js, with no access to files, environment variables or the network, and without threads or the ability to start processes. The engine's own target, wasm32-unknown-unknown, has no standard way to run Rust's test harness; both targets compile the code to the same WebAssembly instructions, and only the WebAssembly runs have `target_arch = "wasm32"` (and a 32-bit `usize`). In WebAssembly a panic aborts the whole test program, so the first failing test stops it, before the harness could print what it captured; that is why nothing is captured there (`--no-capture`), so the failure's message and the test's output appear as they happen. `#[should_panic]` tests are skipped there (the test harness marks them ignored), and a test that reads files, starts a thread or needs a panic to be caught (such as bayan-engine's tests that make the engine panic and check that it recovers) runs on the host only, under `#[cfg(not(target_arch = "wasm32"))]`, with a comment that says why. On a test module, write that condition as a second attribute after `#[cfg(test)]`, not combined with it in `cfg(all(…))`: Clippy treats code as test code, where `unwrap()` is allowed, only under a plain `#[cfg(test)]`.
5. `wasm32`: `cargo build --workspace --exclude bayan-cli --exclude bayan-ffi --exclude bayan-lab --exclude xtask --target wasm32-unknown-unknown --locked`, with warnings as errors. Every crate is built for WebAssembly unless `NATIVE_ONLY` in `xtask/src/verify.rs` lists it with a reason.
6. `doc`: `cargo doc --workspace --no-deps --locked`, with warnings as errors.
7. `deny`: `cargo deny --locked check` (security advisories, licenses, banned or duplicate crates, sources).
8. `guardrails`: checks that the workspace lints forbid `unsafe_code` and `clippy::disallowed_methods`, that every crate inherits the workspace lints, that the copies in bayan-ffi and bayan-wasm have not drifted, that `rust-version` equals the pinned toolchain, and that `clippy.toml` still forbids everything ADR-0005 requires; then compiles each case of `xtask/lint-canary`, a crate configured like the core crates, with the project's real compiler flags and in its own build folder, and checks that Clippy or the compiler rejects it (or, for the two cases that must pass, accepts it: the sanctioned `#[expect]` exception, and the explicit comparison that replaces the forbidden float `clamp`). Among the rejected cases are exceptions to the float bans written in the code, at crate, module and item level and for the groups `clippy::style` and `clippy::all`; each must fail with error E0453. The canary proves the rules work; the inheritance check and the preflight make sure they reach every crate, and the forbidden level makes sure no crate's code can switch the float bans off.
9. `determinism`: the hook for determinism checks (ADR-0025 §1). It runs the fixed test vector of bayan-units' deterministic math (`crates/bayan-units/tests/determinism.rs`) on the host and in WebAssembly, and shows the fingerprints each run prints; both runs compare them with the fingerprints committed in that file, so a pass on the three CI systems means four platforms produced the same bits (CORE-002). Later checks (CORE-003 onward) plug in here too.

Each step prints its command, so a failing step can be re-run by itself. Never skip, weaken or disable a step to make a change pass (`docs/AGENTS.md` §4). Three more workflows run on every pull request, as in every BayanDocs repository: the DCO check (`.github/workflows/dco.yml`; the rules are in `CONTRIBUTING.md`), `reuse lint` (`.github/workflows/reuse.yml`), and the supply-chain checks (`.github/workflows/supply-chain.yml`, also nightly), which fail when configuration for an update bot such as Dependabot or Renovate appears (ADR-0017 rule 1) and audit the hash-pinned Python tools of CI with pip-audit. All three run the pull request's own copy of their files, so a pull request can change the checks that judge it: treat every change under `.github/` as security-relevant in review.

Every Cargo command prints `warning: ignoring registry.global-min-publish-age without -Zmin-publish-age`. That is expected until the toolchain is Rust 1.100; keep the setting.

## Engine artifacts

Work package CORE-007 builds two artifacts for the shells, and drivers that test them the way a shell uses them:

- `cargo xtask sdk [--target <triple>]` builds the **C SDK** for the host (or the target) in `target/artifacts/bayan-core-sdk-<triple>/`: the static and the dynamic library, `include/bayan_ffi.h`, the protocol's JSON Schema, and the licence texts the binaries need, in the layout bayan-desktop's `src/engine/README.md` expects. `cargo xtask c-driver` compiles the C driver, `crates/bayan-ffi/c-driver/driver.c` (plain C11), against that SDK twice, linked statically and dynamically, and runs both; on Windows, run it from a Visual Studio developer environment.
- `cargo xtask wasm-package` builds the **WebAssembly package** in `target/artifacts/bayan-core-wasm/`: the engine module and wasm-bindgen's glue, the worker host `bayan-worker.js`, the protocol's JSON Schema and TypeScript declarations, the test page and the licence texts. It needs the `wasm-bindgen` tool at the version of the wasm-bindgen crate in `Cargo.lock`, which `scripts/dev-setup.sh` installs. `node crates/bayan-wasm/js/tests/node-driver.mjs target/artifacts/bayan-core-wasm` runs the Node.js driver (Node.js 24, no npm packages), which runs the worker host in a worker thread that imitates a browser's. For the test page, serve the package folder over HTTP (for example `python3 -m http.server -d target/artifacts/bayan-core-wasm`) and open `test-page.html`.
- `cargo xtask miri` runs bayan-ffi's unit tests under Miri, on the nightly toolchain that `scripts/dev-setup.sh` installs with it.

Both drivers print `tile <digest>` for the same tile; `.github/workflows/artifacts.yml` builds the SDK on Linux x86-64, Windows x86-64 and macOS arm64 and the WebAssembly package on Linux, runs the C driver on every SDK and the Node.js driver on all three systems, checks that all six rendered the same tile (a driver job that failed or was skipped fails that check too), runs Miri, and uploads the SDKs and the package with SHA-256 checksums. Both drivers must leave standard error empty: they make the engine panic on purpose, and the engine prints nothing, panics included, because a message could quote document content. The workflow uses no cache: the artifacts are distributed, so they are built from a fresh checkout and fresh downloads, never from files a cache restored. Each artifact carries `THIRD-PARTY-LICENSES.txt`, the licences of the crates compiled into it (`xtask/src/notices.rs`, which fails on a crate without a licence file or with an Apache-2.0 NOTICE file), and the Rust standard library's notices.

Generated files are committed and checked by tests, so a change to the protocol's Rust types or to the C interface fails the gate until they are regenerated and reviewed: `BAYAN_UPDATE_GENERATED=1 cargo test -p bayan-engine --test engine` rewrites `crates/bayan-engine/protocol/engine-protocol.schema.json` and `engine-protocol.d.ts`, and `BAYAN_UPDATE_GENERATED=1 cargo test -p bayan-ffi --test header` rewrites `crates/bayan-ffi/include/bayan_ffi.h`. `bayan-cli protocol schema` and `bayan-cli protocol typescript` print the first two.

## Lint rules and exceptions

- Floating-point methods whose result is not exactly specified are forbidden in every crate, with no exceptions, because ADR-0005 §4 allows floating point only as exact IEEE-754 basic operations: platform math such as `sin`, `exp` and `powf`, whose results differ between platforms (use the deterministic functions in bayan-units); the `algebraic_*` methods, which let the compiler reorder or fuse operations (use the plain `+ - * / %` operators); and `min`, `max` and `clamp`, which may return `+0.0` or `-0.0` non-deterministically (compare explicitly, as in `if a > b { a } else { b }`). Arithmetic, `sqrt`, `mul_add`, rounding, sign and comparison methods are exact and allowed. The full list, with the reason for each, is in `clippy.toml`. The lint behind these bans, `clippy::disallowed_methods`, is set to `forbid`, so no code can make an exception: `#[expect]` or `#[allow]` of it, or of a group that contains it such as `clippy::style` or `clippy::all`, fails to compile with error E0453 when Clippy runs. (A plain `cargo build` does not run Clippy and does not notice; the gate's Clippy step does.)
- `HashMap` and `HashSet` are forbidden because their iteration order is random (ADR-0005 §5); use `BTreeMap` and `BTreeSet`.
- `unsafe` code is forbidden everywhere except bayan-ffi and bayan-wasm. There it is still denied by default and allowed only where `#[expect(unsafe_code, reason = "…")]` marks it, and every `unsafe` block needs a `// SAFETY:` comment (ADR-0006 §2).
- Engine code never prints, never calls `unwrap()` outside tests, and never exits the process; documented errors and panics, and explicit numeric conversions, are required. `Cargo.toml` explains each lint.
- Never add a `clippy.toml` or `.clippy.toml` anywhere below the repository root, and never set the `CLIPPY_CONF_DIR` environment variable (also not in the `[env]` table of `.cargo/config.toml`). Clippy does not merge configuration files: for each crate it reads only the nearest one above the crate's folder, so such a file would replace the root `clippy.toml`, bans included, for every crate beneath it. Put every Clippy setting in the root `clippy.toml`; the gate rejects any other configuration.
- Never pass compiler flags that lower lint levels or unlock unstable features: `--cap-lints` (which lowers even `forbid`), `-A`/`--allow`, `--force-warn`, `-Z` options or `@file` arguments, through `RUSTFLAGS` and its relatives or `rustflags` in `.cargo/config.toml`, and never set `RUSTC_BOOTSTRAP`. The preflight rejects them. Other flags, such as `-C target-feature=…` for WebAssembly, are fine.
- Never run the compiler through a wrapper or a replacement program: no `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER` or `RUSTC` (or their `CARGO_BUILD_…` forms), and no `rustc-wrapper`, `rustc-workspace-wrapper` or `rustc` in `[build]` of `.cargo/config.toml`. Such a program sees every compiler call and could weaken the lints for one chosen crate where nothing would notice, so the preflight rejects it. That includes compiler caches such as sccache; unset the variable while you run the gate.
- Choose configurations only with the approved conditions. In `#[cfg(…)]`, `cfg!(…)` and the first argument of `#[cfg_attr(…, …)]`, code may use only `test`, `debug_assertions` and `target_arch = "wasm32"`, combined with `all`, `any`, `not`, `true` and `false`; the Clippy step checks the code under every combination of their values, so nothing under them escapes Clippy. The preflight rejects every other condition, for example `feature = "…"`, `windows`, `unix`, `target_os = "…"`, any other `target_arch`, `clippy`, `miri`, `doc` or a name of your own: code under it would be compiled in a configuration that Clippy never checks, where none of the bans apply. Only the lint canary's crate may use its switch `bayan_lint_canary = "…"`. To approve another condition, add it to `APPROVED_CONDITIONS` in `xtask/src/verify.rs` with its reason, together with the Clippy runs in `CLIPPY_RUNS` that check the code with it both on and off, in a reviewed pull request; the unit test `the_clippy_runs_check_every_combination_of_the_approved_conditions` fails otherwise. Feature flags are not approved: make optional support, such as `serde`, unconditional, or approve `feature = "…"` together with Clippy runs that switch it on and off. Clippy checks the dev and release profiles; a work package that builds or ships with another profile adds it to `CLIPPY_RUNS`.
- Write every condition out in full. A condition may not contain a macro's metavariable (`$`), and the words `cfg` and `cfg_attr` may stand only directly before their condition (`cfg(`, `cfg!(` and `cfg_attr(`), so that no macro can build a condition from what it is handed: a `macro_rules!` matcher such as `$tool:ident :: $lint:ident`, handed the lint path `clippy::disallowed_methods`, could otherwise keep only `clippy` and write `#[cfg(not($tool))]`, and a macro handed the word `cfg` could write `#[$name(…)]`. Every other word that starts with `cfg` is rejected too, so never give anything a name that starts with `cfg`: `cfg_select!`, which the pinned toolchain offers, chooses code by conditions that are not written inside `cfg(…)`, and later Rust versions may add more such macros. Write `#[cfg(…)]` on the items instead, and `cfg!(…)` with round brackets.
- Never hide code from Clippy behind its own condition. Clippy sets the condition `clippy` when it compiles a crate and a normal build does not, so code under `#[cfg(not(clippy))]` would be compiled, tested and shipped but never linted. Besides rejecting it as a condition, the preflight rejects the bare identifier `clippy` (not followed by `::`) anywhere in the workspace's Rust files outside comments and strings: as an argument handed to a macro such as `m!(clippy)`, and as the name of a variable or function. Lint paths such as `clippy::unwrap_used` are fine; name things `clippy_config` or similar.
- Inside a macro, write every attribute out in full. A `macro_rules!` macro could write any attribute from what it is handed, such as `#[$attribute] mod sine;` handed `path = "…"`, so the preflight rejects an attribute that contains a metavariable anywhere outside the macro's matchers (the patterns its input must match). An attribute stays an attribute when its `#` and `[` are written apart, so the preflight also rejects the split forms found so far (the others pass the compiler but mean something else, so there is no reason to write them): a `#` must be written directly against the `[` or `![` it opens — a `#` that any other token follows is rejected, both in the code a macro writes (`# $attribute …`, which becomes `#[…]` when `$attribute` is a bracket group) and in what is handed to a macro (`m!(#, …)`, which hands it a bare `#`); and a `[…]` written directly after a metavariable (`$name [ … ]`), a repetition (`$( … )* [ … ]`), or either with a `!` between (`$name ![ … ]`) is read as an attribute, because the substitution before it could expand to `#` or `#!`. If a `[…]` after a metavariable is really an index, bind it first: `let index = $index; $array[index]`. The one exception passes on an attribute exactly as it was written where the macro is called, such as a doc comment, which the preflight checks there: bind it with `$(#[$meta:meta])*` in the matcher and write it as `$(#[$meta])*`, with the `#` against its bracket. Document the items a macro creates with doc comments where the macro is called, not with `#[doc = $text]`. These rules do not catch every split form yet: a macro can keep the `#` of an attribute written in full where it is called, drop that attribute's bracket, and write the `#` before a bracket group handed in separately (`($hash:tt $dropped:tt, $bracket:tt) => { $hash $bracket mod hidden; }`, called as `m!(#[doc = "…"], [path = "…"])`, or without the comma), which builds a `#[path]` that the preflight does not see. Issue #7 closes this for every form that makes the compiler read a file, by comparing the files the compiler read during the Clippy runs with the files the preflight read; until then, reviewers check every macro that takes a `#` or a bracket group as a `tt`.
- Keep every Rust file where the gate reads it. The preflight reads every `.rs` file below the folders of the workspace members (it skips only the build folder `target/` at the root) and rejects what would make the compiler read any other file: `include!` (the identifier `include` anywhere outside comments and strings, so never name anything `include`; `include_str!` and `include_bytes!` read data and are fine); the attribute `#[path = "…"]`, also inside `cfg_attr` and, as far as the previous item reaches, from a macro's arguments; a symbolic link in a member's folder; a file named like `sine.RS`, which Windows and macOS also find as `sine.rs`; and a target whose root file lies outside its crate's folder or does not end in `.rs` (a path in `[lib]`, `[[bin]]`, `[[test]]`, `[[bench]]` or `[[example]]`, or `build = "…"`, moves it). Declare modules with a plain `mod name;` and keep their files where the compiler looks by default (`name.rs` or `name/mod.rs`). Never make a member depend by path on a crate that is not a workspace member, for example one in the excluded folder `fuzz/`: Cargo compiles such a crate without Clippy, and the preflight does not read it. `cargo xtask check-exact-pins`, in the gate's supply-chain step, rejects such a dependency, and `cargo xtask check-lockfile-age` rejects a crate that Cargo builds from a folder through `[patch]`, `[replace]` or `paths`.
- No crate has a build script (`build.rs`, or `build = "…"` in its manifest) unless `BUILD_SCRIPTS` in `xtask/src/verify.rs` lists it with a reason; the preflight rejects any other. A build script runs code during the build and can change how its crate is compiled, so a build script must never set Clippy or compiler variables through `cargo::rustc-env` (for example `CLIPPY_CONF_DIR`, which would switch off the root `clippy.toml` for that crate), and reviewers read every listed build script, and every change to one, in full.
- No crate is a procedural-macro crate (`proc-macro = true` in `[lib]`) unless `PROC_MACROS` in `xtask/src/verify.rs` lists it with a reason; the preflight rejects any other. A procedural macro runs code while the compiler compiles the crates that use it, and can produce any code, hidden conditions included, without that code appearing in a source file, so the source check cannot see what it writes. Reviewers read every listed macro, and every change to one, in full. Both lists start empty, and the preflight also rejects an entry that names no workspace member or a member without such a target, so they cannot go stale. Procedural macros from dependencies, such as serde's derive, are not affected; they are reviewed with the dependency (ADR-0017).
- The only way to make an exception is `#[expect(lint_name, reason = "why this is safe")]` on the smallest item that needs it. `#[allow]`, and exceptions without a reason, are rejected; an `#[expect]` that is no longer needed fails the build, so exceptions cannot go stale. Clippy's own hint to "add `#[allow(…)]`" does not apply here. The float-method bans have no exceptions, because ADR-0005 §4 allows none, and the compiler enforces that (see the first item). `#[expect(clippy::disallowed_types, reason = "…")]` is only for a hash map or set whose iteration order cannot affect any output, and the reason must say why.

## Adding a crate

1. Create `crates/<name>/` with a `Cargo.toml` like the existing crates' (every `[package]` field taken from the workspace, plus `[lints]` with `workspace = true`), and make sure the crate is in the crate map of `docs/plan/03-architecture.md`.
2. Start `src/lib.rs` with crate documentation that states the crate's responsibility, its layer and the layering rule (copy the wording of an existing crate), followed by `#![forbid(unsafe_code)]`.
3. Depend only on crates of the same layer or below. Declare third-party dependencies once in `[workspace.dependencies]` of the root `Cargo.toml`, with an exact `=x.y.z` version, and justify each in the pull request (ADR-0017).
4. If the crate cannot run in a browser, such as a command-line tool, add it to `NATIVE_ONLY` in `xtask/src/verify.rs` with the reason; otherwise the gate builds it for WebAssembly, and Clippy checks it there too.
5. Avoid a build script, and do not make the crate a procedural-macro crate. If the crate really needs either, add it to `BUILD_SCRIPTS` or `PROC_MACROS` in `xtask/src/verify.rs` with the reason (see "Lint rules and exceptions").
6. Use only the approved conditions (`test`, `debug_assertions` and `target_arch = "wasm32"`), written out in full. If the crate needs another, such as a feature flag, approve it first, together with the Clippy runs that check it (see "Lint rules and exceptions").
7. Run `cargo xtask verify`.

Spike and Fidelity Lab crates live in `spikes/` and `lab/` and are added to `members` in the root `Cargo.toml` by name; see the READMEs there.

## Toolchain

Rust is pinned to 1.99.0 (released 2026-10-01) in `rust-toolchain.toml`, with the targets wasm32-unknown-unknown (the web app's engine) and wasm32-wasip1 (the tests in WebAssembly); rustup installs a missing target by itself on first use, or `scripts/dev-setup.sh` does it ahead of time. The version is also the minimum supported version (`rust-version` in `Cargo.toml`, ADR-0006 §7). Change it only in the monthly dependency session, to the newest stable release that is at least 24 hours old, in three places at once: `rust-toolchain.toml`, `rust-version` in `Cargo.toml` (the gate checks that they are equal), and `RUST_STABLE` in the docs repository's `scripts/cloud-environment-setup.sh`. Rust 1.100 (2026-11-12) is the first release that enforces `global-min-publish-age`; adopt it in the first session after it is 24 hours old.

## Dependency mechanisms

Exact `=x.y.z` requirements in `[workspace.dependencies]`, which `cargo xtask check-exact-pins` checks together with every member's dependencies; `Cargo.lock` committed and every build runs with `--locked`; `.cargo/config.toml` sets `global-min-publish-age = "1 day"`, which Cargo enforces from Rust 1.100, and only when it resolves new versions. `cargo xtask check-lockfile-age` therefore checks every package version that a pull request adds to `Cargo.lock`: it reads the publish time from the crates.io sparse index (`pubtime`), or from the crates.io API (`created_at`, at most one request per second) for a version without one, sends a User-Agent that names the tool and this repository, and fails if the version was published less than 24 hours before the commit that added it, or before now, or if its checksum in `Cargo.lock` is not the one crates.io published. Before that it makes sure that `Cargo.lock` is what Cargo builds: the packages `cargo metadata` resolves must be exactly those of `Cargo.lock`, no package outside the workspace may be built from a folder (`[patch]`, `[replace]`, `paths`, vendored sources), and the file must be in the exact layout Cargo writes. A package that the change adds from a Git repository fails too: it has no crates.io publish time or checksum to check. Its code, in `xtask/src/supply_chain/`, is identical in bayan-server; its tests replay recorded crates.io answers (`xtask/src/supply_chain/fixtures/`), so they never use the network. `cargo deny check` runs in the gate on every pull request and every night with `deny.toml`: RustSec advisories (unmaintained and unsound crates anywhere in the build, and yanked versions, fail), the ADR-0017 license allowlist, duplicate versions as warnings, and crates.io as the only source; a Git dependency would need an `allow-git` entry and a fixed `tag` or `rev`, and `cargo xtask check-lockfile-age` refuses every package from a Git repository that a change adds, because it cannot judge a commit's age yet (the work package that needs a Git dependency teaches it first). `deny.toml` ignores six advisories, each with its reason, all for crates that Loro (ADR-0008) depends on and none with a fixed version, accepted by the owner on 2026-10-08 (ADR-0008, amendment 2026-10-08; `spikes/crdt-model/REPORT.md` §10): four say that im, sized-chunks, bitmaps and atomic-polyfill are unmaintained, and two that im and sized-chunks are unsound in code that Loro does not reach. Every monthly dependency session re-checks them (the docs repository's `developer/dependency-update-runbook.md`): each reason must still hold, and each is removed as soon as Loro no longer needs its crate (Loro is asked to move to the maintained replacements, imbl and imbl-sized-chunks); every other advisory fails the gate. The supply-chain workflow (`.github/workflows/supply-chain.yml`, the same in every BayanDocs repository) fails on update-bot configuration and runs pip-audit on the hash-pinned Python tool requirements, on every pull request and nightly. Tools used in CI are pinned and checksum-verified: cargo-deny 0.20.2 in `.github/workflows/verify.yml`, matched by `CARGO_DENY_VERSION` in `xtask/src/verify.rs` (a test keeps them equal); Node.js 24.21.0 in the same workflow and in `scripts/dev-setup.sh`, matched by `NODE_VERSION` in `xtask/src/verify.rs` (a test keeps them and the copy in `.github/workflows/artifacts.yml` equal), checked against the SHA-256 checksums of nodejs.org's signed `SHASUMS256.txt`; GitHub Actions are pinned to full commit SHAs. xtask itself has no dependencies. Routine upgrades happen only in the monthly dependency session, following the docs repository's `developer/dependency-update-runbook.md`.

CORE-007 added these pins. **wasm-bindgen**, the tool of the wasm-bindgen-cli crate (`WASM_BINDGEN_VERSION` in `scripts/dev-setup.sh` and `.github/workflows/artifacts.yml`), must equal the wasm-bindgen crate in `Cargo.lock`, because the two halves of wasm-bindgen's glue must match: xtask tests and `cargo xtask wasm-package` check it. Both install the project's release archive, checked against a pinned SHA-256 (equal to the `.sha256sum` file published with it; a test keeps the Linux x86-64 pin the same in both). `scripts/dev-setup.sh` leaves a `wasm-bindgen` of that version already on `PATH` alone, and builds from crates.io (`cargo install --locked --no-default-features`, 149 crates, no C code, but with the test runner's crates, four of them unmaintained and one yanked; see the script's header) only where it pins no archive or the download fails.
