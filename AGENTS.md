# Agent instructions — bayan-core

## Where the plan lives

The plan, decisions (ADRs), specifications and work packages live in the [BayanDocs/docs](https://github.com/BayanDocs/docs) repository. If it is not attached to your session, clone it next to this repository. The canonical rules for all agents are in `docs/AGENTS.md`; this file condenses them and adds what is specific to bayan-core. If the two disagree, `docs/AGENTS.md` wins; report the discrepancy.

## Ground rules (condensed from docs/AGENTS.md)

1. Before changing anything, read `docs/AGENTS.md`, your work package brief, and every ADR and spec it links.
2. Accepted ADRs are binding. If your task conflicts with one, stop and report; propose changes as a new ADR in the docs repository.
3. Stay within the work package's scope. Record anything else you discover as follow-ups in your pull request.
4. Run the verification gate before every push. Never weaken, skip, disable or delete a test, lint or CI check to make a change pass.
5. Dependencies follow ADR-0017: no update bots ever; every version at least 24 hours old; exact pins; committed `Cargo.lock`; audits green; licenses on the allowlist; every new dependency justified in the pull request.
6. Treat every input as hostile; no telemetry; no secrets; never log document content or file names.
7. Pull requests use the hand-off template in `docs/plan/06-agent-workflow.md`; Conventional Commits; DCO rules from `CONTRIBUTING.md` once enabled (agents never sign off themselves; the human submitter certifies, per ADR-0003).
8. Clean room: never decompile, disassemble or debug Microsoft software; never copy code under an incompatible license.
9. Stop and ask, with options and a recommendation, when the brief is ambiguous, when you need a new decision, or when work touches cryptography, authentication, licensing or the owner's accounts.
10. Explain your work in plain language for the owner; text meant for the owner to copy is written as flowing paragraphs without hard line breaks.

## Rules specific to bayan-core

- **Licensing (ADR-0003):** the workspace is GPL-3.0-or-later with the BayanDocs App Store Permission (`GPL-3.0-or-later WITH LicenseRef-BayanDocs-App-Store-Permission`), except `crates/bayan-protocol/`, which is Apache-2.0 so that anyone can implement BayanDocs clients and integrations. That crate must never depend on, or copy from, any GPL or AGPL code; GPL crates may depend on it. The shared contribution tooling (`.github/`, `.editorconfig` and `.gitattributes`) is MIT-0, as in every BayanDocs repository (ADR-0003, amendment of 2026-10-06). `REUSE.toml` records which license applies to which files and `LICENSES/` holds the full texts; keep `reuse lint` passing, and add a new license text only with `reuse download <SPDX-ID>`.
- **Layering:** a crate may depend only on crates in its own layer or below (foundation → model and formats → text → layout → output → interaction → engine → bindings and tools). Never add an upward dependency.
- **Determinism (ADR-0004, ADR-0005):**
  - layout arithmetic uses integer BLU types from `bayan-units`, never floating point;
  - no platform floating-point transcendental functions (`sin`, `exp`, `powf`, …) anywhere in the core; use `bayan-units` (the full list of forbidden float methods is under "Lint rules and exceptions");
  - no output that depends on hash-map iteration order (use ordered maps or deterministic hashers);
  - no system time, locale, environment variables, installed fonts or thread scheduling in anything that affects output unless passed in by the host.
- **Safety (ADR-0006):** `#![forbid(unsafe_code)]` everywhere except `bayan-ffi` and `bayan-wasm`; no C or C++ libraries for parsing untrusted input; every parser enforces size, depth and count limits and has a fuzz target; panics never cross the FFI or WebAssembly boundary.
- **No outside world:** the core never opens sockets, reads arbitrary files, or calls platform APIs; it asks the host through the engine protocol's host services (ADR-0012). The gate enforces part of this: the code that ships of every crate that `OUTSIDE_WORLD` in `xtask/src/verify.rs` does not list names none of the five modules of Rust's standard library that exist for the outside world, `std::env`, `std::fs`, `std::net`, `std::process` and `std::time` (see "Lint rules and exceptions", which also says what that check does not see), and `cargo xtask wasm-package` fails on any import of the engine's WebAssembly module that `WASM_IMPORTS` in `xtask/src/artifacts.rs` does not list (see "Engine artifacts"). The engine's thread has a stack of a fixed size (`ENGINE_THREAD_STACK_BYTES` in `crates/bayan-engine/src/thread.rs`, 2 MiB), so that the `RUST_MIN_STACK` environment variable does not decide how deeply an input may nest.
- **Active content (ADR-0023):** never fetch external resources referenced by documents, never execute macros, DDE or OLE.
- **Layout changes:** any change that alters layout output for corpus documents needs Fidelity Lab evidence in the pull request, the `fidelity-change` label, and a layout-epoch increment when intentional (ADR-0004, ADR-0025).
- **Lab data:** corpus documents are never committed to Git (only manifests); Microsoft font files or full metric tables never leave the reference machine; private-corpus content never appears in logs, reports or test snapshots.

## Verification gate

Run `cargo xtask verify` before every push, from anywhere in the repository. CI runs the same command on `ubuntu-24.04`, `windows-latest` and `macos-latest` (arm64) for every pull request, every push to `main`, and every night. It needs rustup, which installs the pinned toolchain from `rust-toolchain.toml` by itself, with its targets; cargo-deny 0.20.2 (`cargo install --locked cargo-deny@0.20.2`; the BayanDocs cloud environment already has it); Node.js 24.22.1, which runs the tests in WebAssembly; and `curl` 7.87 or later, which bayan-lab's storage tests run (macOS, Ubuntu 24.04 and up-to-date Windows 10 and 11 include one; the tests say so when curl is older). `scripts/dev-setup.sh` installs the toolchain's targets and, on Linux and macOS, Node.js with a verified checksum, and prints how to put it on PATH. In BayanDocs cloud sessions Node.js is preinstalled in `/opt/bayandocs/node/bin`, but only login shells have it on PATH, so start each shell command with `. /etc/profile.d/zz-bayandocs.sh` (or `export PATH="/opt/bayandocs/node/bin:$PATH"`); the environment is updated in batches (docs issue #7), so when its version differs from `NODE_VERSION`, run `scripts/dev-setup.sh`, which installs the pinned one, and put that first on PATH instead. Before it builds anything, a preflight checks that the toolchain, cargo-deny and Node.js match their pins; that Clippy reads only the root `clippy.toml` (no other `clippy.toml` or `.clippy.toml` anywhere in the repository, and no `CLIPPY_CONF_DIR` environment variable); that no compiler flag lowers lint levels or unlocks unstable features (`--cap-lints`, `-A`/`--allow`, `--force-warn`, `-Z` options and `@file` arguments in `RUSTFLAGS`, `CARGO_ENCODED_RUSTFLAGS`, `CARGO_BUILD_RUSTFLAGS`, `CARGO_TARGET_<TRIPLE>_RUSTFLAGS` or the `rustflags` of `.cargo/config.toml`, and the `RUSTC_BOOTSTRAP` variable); that Cargo runs no wrapper or replacement in place of the compiler (`RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER`, `RUSTC` and their `CARGO_BUILD_…` forms, or `rustc-wrapper`, `rustc-workspace-wrapper` and `rustc` in `[build]` of `.cargo/config.toml`); that no workspace member has a build script or is a procedural-macro crate unless `BUILD_SCRIPTS` or `PROC_MACROS` in `xtask/src/verify.rs` lists it, and that neither list names a crate that has none; that every member that `OUTSIDE_WORLD` in `xtask/src/verify.rs` names exists, and that no other member depends on one of them except for its tests (see "Lint rules and exceptions"); and that the workspace's Rust files use only the approved conditions, written out in full, build no condition or attribute from a macro's arguments, never use the bare identifier `clippy`, and make the compiler read no file that the gate does not read (see "Lint rules and exceptions"). Then it runs these steps in order and stops at the first failure:

1. `supply-chain`, first, so that no code of a dependency it rejects is compiled or run (its build script, procedural macros or tests) before it fails; it builds nothing itself. Both of its checks read every Cargo workspace of the repository: the main one, and every folder below it where Git tracks a `Cargo.lock`, today the fuzz workspace (`fuzz/`), which may also depend by path on members of the main workspace and on nothing else outside itself (bayan-core#22); a `Cargo.lock` in a folder that Cargo does not read as the root of a workspace, or one named in another letter case, fails both, and so does a `Cargo.toml` that Git tracks but that is neither the root manifest nor a member of a checked workspace, which Cargo could build as a workspace of its own from a lockfile that was never committed. `cargo xtask check-exact-pins` checks that every dependency is pinned exactly: each entry of `[workspace.dependencies]` as written, and each dependency of every member as `cargo metadata` resolves it (an exact `=x.y.z` requirement for crates.io, a path only to a member of the same workspace or, from `fuzz/`, of the main workspace, a Git dependency only at a fixed `tag` or `rev` with a full commit hash); then `cargo xtask check-lockfile-age`, which first checks that Cargo builds exactly the packages of each `Cargo.lock` (the packages `cargo metadata --all-features` resolves must be the same, as Cargo resolves the lockfile with every feature of the members switched on, so neither another lockfile set with `resolver.lockfile-path` nor a crate built from a folder through `[patch]`, `[replace]`, `paths` or vendored sources can pass, the fuzz workspace may build only members of the main workspace from their folders, and a package added from a Git repository fails), and then that every package version the change adds to a `Cargo.lock` since the merge base with `origin/<GITHUB_BASE_REF>` (in a pull request on GitHub Actions) or `origin/main` (compared with that lockfile's own version there, and in full if it did not exist there) was published on crates.io at least 24 hours before the commit that added it, and before now, with the checksum crates.io published. It reads each `Cargo.lock` only in the exact layout Cargo writes and fails on any other spelling. The age check needs the full Git history and `curl`, asks crates.io only when a `Cargo.lock` changed, and lets `cargo metadata` download the crate files that Cargo's cache lacks (without building anything). Both are also commands of their own; `cargo xtask check-lockfile-age --base <revision>` compares with another branch.
2. `fmt`: `cargo fmt --all --check`.
3. `clippy`: Clippy four times, for the host and for `wasm32-unknown-unknown`, each in the dev and the release profile, every warning an error: `cargo clippy --workspace --all-targets --all-features --locked --message-format=json-render-diagnostics -- -D warnings`, the same with `--release`, and both again with `--target wasm32-unknown-unknown` and without the `NATIVE_ONLY` crates. `--all-targets` compiles every crate both with and without `test`, the dev profile switches `debug_assertions` on and the release profile off, and only the WebAssembly runs have `target_arch = "wasm32"`, so together the runs compile the code under every combination of the approved conditions. The runs (`CLIPPY_RUNS`) and the conditions (`APPROVED_CONDITIONS`) stand side by side in `xtask/src/verify.rs`, and a unit test fails unless the runs cover every combination of the conditions' values. The WebAssembly runs set no `RUSTFLAGS`, so they read the compiler flags of `.cargo/config.toml`, unlike the `wasm32` step. After each run the step checks what the compiler actually read (`xtask/src/dep_info.rs`, bayan-core#7): for every unit of a workspace member in that run, it reads the dependency file (dep-info, `.d`) that the compiler wrote, which lists every file the compiler read for the unit, and fails if one of them is not a file that the preflight's source check read, unless it is one of Clippy's own two files (`Cargo.toml` and the root `clippy.toml`, named exactly as Clippy names them) or a data file that `DATA_FILES` in `xtask/src/verify.rs` lists for that member (see "Lint rules and exceptions"). The error names the run, the unit and each file, relative to the root. The step takes the units from Cargo's JSON messages, fresh ones included, never from the build folder, which keeps the dependency files of earlier builds and of the other steps; `--message-format=json-render-diagnostics` still prints the diagnostics for people on standard error. It fails on anything it cannot follow: a member that the run checks without a unit, a unit without a dependency file, a unit that Cargo compiled in the run (`"fresh": false` in its message) whose dependency file was last written before the run began (rounded down to the second, for file systems that store whole seconds), so that a file left over from an earlier build can never stand in for the record of this one, a line it cannot read, a listed file that does not exist, and a list without the unit's own root file. After the last run it fails if a member that an entry of `DATA_FILES` names read the entry's files in none of the runs, and then runs the outside-world check on the code that ships, every line of the Rust files that the dependency files of the units that are not tests list (`xtask/src/outside_world.rs`; see "Lint rules and exceptions"). Last comes the lint audit (`xtask/src/lint_audit/`, CORE-009). It compiles an empty crate with rustc to check that the pinned compiler still refuses to force-warn exactly the lints of its skip list, then runs Clippy again for each of the four runs, with the same platform and profile and the same arguments up to the message format, twice: first for the units that are not tests (`--lib --bins --examples` in place of `--all-targets`), then for all targets, so that it can tell the units compiled as tests from the others, both with `--message-format=json` and with `--force-warn <lint>` after `--` for every guarded lint in place of `-D warnings`. The guarded lints are every lint and group that a lint table sets to `warn` or `deny` (`[workspace.lints]` in the root `Cargo.toml` and the copies in bayan-ffi's and bayan-wasm's manifests) and every lint that the pinned compiler turns on by default for the workspace's edition (`rustc --edition 2024 -W help`), except those of the skip list; the preflight reads them and prints how many there are. It reads a lint table only in its plain form, each entry written as `name = "level"` or `name = { level = "…", priority = … }` directly in `[workspace.lints.<tool>]` or `[lints.<tool>]` for rust, clippy or rustdoc, and fails on every other form of TOML that Cargo would read the same way (a table below a tool's table such as `[workspace.lints.clippy.all]`, a dotted or quoted key, an entry of `[workspace.lints]` itself, and keys of an entry's inline table other than `level`, `priority` and `check-cfg`), because it would not see what such a form sets. A force-warned lint is reported wherever it occurs, also where an attribute silences it, as a warning that ignores `-D warnings`, so the audit runs judge nothing by their exit status: the step fails on every occurrence they report that no `#[expect(<lint>, reason = "…")]` written out in full in the source covers, naming the lint, the file, the line and the macro that wrote the code there, and on any message it cannot read, a member without a unit, a member's target compiled for another edition than the workspace's (whose default lints it force-warns), a run that did not finish, and a list of guarded lints that comes out empty (see "Lint rules and exceptions"). Where the second invocation replays the messages of a target's unit that is not a test from the first, because it finds that very unit unchanged, what it reports beyond the first for that target comes from tests. The audit checks that replay with Cargo's `compiler-artifact` messages instead of assuming it, because it often does not happen: without the tests and their dev-dependencies, Cargo can resolve the features of some dependencies differently (syn's, for one), so the first invocation checks those dependencies again in another variant on a cold build folder, and compiles another unit of each member that uses them, which the second invocation then compiles again. For a target whose unit that is not a test the second invocation did not replay, the audit judges every occurrence both as a test and as not a test, so that an exception inside `cfg_attr` counts only if it holds both ways. The audit runs share the build folder with the Clippy runs; their arguments differ, so Cargo recompiles the members in each.
4. `test`: `cargo test --workspace --locked`, then the same tests in WebAssembly: `cargo test --workspace --exclude bayan-cli --exclude bayan-ffi --exclude bayan-lab --exclude xtask --locked --target wasm32-wasip1 --config 'target.wasm32-wasip1.runner = ["node", "--disable-warning=ExperimentalWarning", "<root>/xtask/wasi-runner.mjs"]' -- --no-capture`. Each test program runs as a WASI program in Node.js, with no access to files, environment variables or the network, and without threads or the ability to start processes. The engine's own target, wasm32-unknown-unknown, has no standard way to run Rust's test harness; both targets compile the code to the same WebAssembly instructions, and only the WebAssembly runs have `target_arch = "wasm32"` (and a 32-bit `usize`). In WebAssembly a panic aborts the whole test program, so the first failing test stops it, before the harness could print what it captured; that is why nothing is captured there (`--no-capture`), so the failure's message and the test's output appear as they happen. `#[should_panic]` tests are skipped there (the test harness marks them ignored), and a test that reads files, starts a thread or needs a panic to be caught (such as bayan-engine's tests that make the engine panic and check that it recovers) runs on the host only, under `#[cfg(not(target_arch = "wasm32"))]`, with a comment that says why. On a test module, write that condition as a second attribute after `#[cfg(test)]`, not combined with it in `cfg(all(…))`: Clippy treats code as test code, where `unwrap()` is allowed, only under a plain `#[cfg(test)]`. A test that measures WebAssembly's memory with `core::arch::wasm32::memory_size` must be the only test of its test program, an integration-test file of its own like bayan-xml's `tests/memory_runs.rs` and `tests/memory_declarations.rs`: linear memory never shrinks and the tests of one program share one instance, so memory that an earlier test grew would hide what the measured test allocates.
5. `wasm32`: `cargo build --workspace --exclude bayan-cli --exclude bayan-ffi --exclude bayan-lab --exclude xtask --target wasm32-unknown-unknown --locked`, with warnings as errors. Every crate is built for WebAssembly unless `NATIVE_ONLY` in `xtask/src/verify.rs` lists it with a reason.
6. `doc`: `cargo doc --workspace --no-deps --locked`, with warnings as errors.
7. `deny`: `cargo deny --locked check` (security advisories, licenses, banned or duplicate crates, sources), then the same for the fuzz workspace with its own `deny.toml`: `cargo deny --locked --manifest-path fuzz/Cargo.toml --config fuzz/deny.toml check`, which differs from the main policy only by accepting libFuzzer's NCSA license for libfuzzer-sys (ADR-0017, amendment of 2026-10-08).
8. `guardrails`: checks that the workspace lints forbid `unsafe_code` and `clippy::disallowed_methods`, that every crate inherits the workspace lints, that the copies in bayan-ffi and bayan-wasm have not drifted, that `rust-version` equals the pinned toolchain, and that `clippy.toml` still forbids everything ADR-0005 requires; then compiles each case of `xtask/lint-canary`, a crate configured like the core crates, with the project's real compiler flags and in its own build folder, and checks that Clippy or the compiler rejects it (or, for the two cases that must pass, accepts it: the sanctioned `#[expect]` exception, and the explicit comparison that replaces the forbidden float `clamp`). Among the rejected cases are exceptions to the float bans written in the code, at crate, module and item level and for the groups `clippy::style` and `clippy::all`; each must fail with error E0453. Three more cases, which Clippy and the compiler accept, are lint exceptions that no one wrote out in full: an `#[allow]` and an `#[expect]` that a macro assembles from the `#` of a doc attribute and a bracket group handed in separately, and an `#[allow]` written in full inside the input of std's `thread_local!`, which puts it out. The canary compiles them with the lint audit's force-warned lints, and the audit must find each lint they silence (the hash-map ban, and `unused_must_use`, which the compiler turns on by default) where no exception written out in full covers it. The canary proves the rules work; the inheritance check and the preflight make sure they reach every crate, and the forbidden level makes sure no crate's code can switch the float bans off.
9. `determinism`: the hook for determinism checks (ADR-0025 §1). It runs the fixed test vector of bayan-units' deterministic math (`crates/bayan-units/tests/determinism.rs`) on the host and in WebAssembly, and shows the fingerprints each run prints; both runs compare them with the fingerprints committed in that file, so a pass on the three CI systems means four platforms produced the same bits (CORE-002). It also lays out and rasterizes the probes of the text pipeline spike whose fonts are committed (`spikes/text-pipeline/tests/determinism.rs`), on the host and in WebAssembly, and checks that they give the layout and reference raster hashes of `spikes/text-pipeline/results/expected.json`, the file that `.github/workflows/text-pipeline.yml` compares the whole probe set with in eleven environments (CORE-003). Later checks plug in here too.

Each step prints its command, so a failing step can be re-run by itself. Never skip, weaken or disable a step to make a change pass (`docs/AGENTS.md` §4). Five more workflows run on every pull request, as in every BayanDocs repository: the DCO check (`.github/workflows/dco.yml`; the rules are in `CONTRIBUTING.md`), `reuse lint` (`.github/workflows/reuse.yml`), the supply-chain checks (`.github/workflows/supply-chain.yml`, also nightly), which fail when configuration for an update bot such as Dependabot or Renovate appears (ADR-0017 rule 1) and audit the hash-pinned Python tools of CI with pip-audit, the workflow lint (`.github/workflows/workflow-lint.yml`, also nightly) and CodeQL (`.github/workflows/codeql.yml`, also weekly), which "Workflow conventions" below describes. All five run the pull request's own copy of their files, so a pull request can change the checks that judge it: treat every change under `.github/` as security-relevant in review.

Every Cargo command prints `warning: ignoring registry.global-min-publish-age without -Zmin-publish-age`. That is expected until the toolchain is Rust 1.100; keep the setting.

## Workflow conventions

GitHub Actions workflows run with access to the repository, so they are part of the supply chain (threat T16 in `docs/specs/threat-model.md`). Every workflow follows the workflow conventions of `docs/AGENTS.md` (§6, from work package X-002):

- **Permissions:** `permissions: {}` at the top of the workflow, and each job asks in its own `permissions:` block for exactly what it needs, with a comment that says why. Most jobs need only `contents: read`.
- **Checkout:** `persist-credentials: false` on every `actions/checkout`, unless the job pushes (none does today).
- **Triggers:** never `pull_request_target`, and never `workflow_run` to act on a pull request's code with more than read access. Workflows that pull requests trigger use no secrets; the automatic `GITHUB_TOKEN`, limited by the permissions above, is the only credential they get. A workflow with a job that `main`'s ruleset requires runs on `merge_group` (`types: [checks_requested]`) as well as on `pull_request`, under the same rules, because the merge queue waits for every required check on the commit it is about to merge, and a check that never runs there takes the pull request out of the queue after a timeout.
- **Limits:** every job has `timeout-minutes` and runs under a `concurrency` group (set once for the whole workflow), so that a newer push to a pull request replaces the older run instead of running beside it.
- **Actions:** only GitHub's own actions (`actions/*`, `github/*`), each pinned to a full 40-character commit SHA with its version in a trailing comment (`uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`), and published at least 24 hours earlier. A third-party action needs the owner's approval and an entry in the allowed list of `docs/scripts/github-settings.py`; prefer a checksum-verified program instead, as the Scorecard workflow does.
- **Tools:** every tool that a workflow downloads is pinned to an exact version that was at least 24 hours old, and is checked against a SHA-256 written in the repository (taken from the publisher's checksum file where there is one) before it runs. Python tools come from hash-pinned requirements files (`pip --require-hashes --only-binary :all:`). Never `curl … | sh`, never "latest".
- **Untrusted text:** never put `${{ … }}` with event data (pull request titles, branch names, commit messages) inside a `run:` script, where it would become shell code; pass it through `env:` and quote the variable.

Three workflows check this. **Workflow lint** (`.github/workflows/workflow-lint.yml`, on every pull request, on pushes to `main` and nightly) runs zizmor, a static analyser for workflows, which must report nothing at its default settings: it reads no configuration file, obeys no ignore comments and also audits workflows that a `.gitignore` names, and it runs its online audits, which find actions with known vulnerabilities. It also runs `pinact run --check --verify-min-age --min-age 1`, which checks every pin and its age. zizmor is pinned in `.github/workflow-lint/requirements.txt` and pinact in the workflow, both equal to the BayanDocs cloud environment's pins. **CodeQL** (`.github/workflows/codeql.yml`, on every pull request, on pushes to `main` and weekly) scans the workflows, the JavaScript of `crates/bayan-wasm/js/`, the WASI runners and the text pipeline spike's runners (`spikes/text-pipeline/js/`), the Python checks in `.github/`, bayan-ffi's C driver and header (without a build) and the Rust workspace. CodeQL's Rust extractor runs `cargo check`, which runs code of the dependencies (build scripts and procedural macros), so its job first runs `cargo xtask check-exact-pins` and `cargo xtask check-lockfile-age`, the gate's first step; the fuzzing workflow does the same before it builds the fuzz targets (bayan-core#22). The extractor installs, with rustup, the Rust version that its release was made for (1.98.1 for CodeQL 2.27.2), which is older than the workspace's 1.99, so today its `cargo check` stops at once and CodeQL reads macros without expanding them. Its engine, the CodeQL bundle, is downloaded by the workflow and checked against the SHA-256 that its release publishes. **Scorecard** (`.github/workflows/scorecard.yml`, weekly and on pushes to `main`) runs the OpenSSF Scorecard program, pinned and checked against its SHA-256, with a read-only token, and rates the repository's practices; `.github/scorecard/policy.yml` chooses which of its checks raise alerts. CodeQL and Scorecard report under Security → Code scanning. In a BayanDocs cloud session, run `zizmor --offline --no-config --no-ignores --collect=all --strict-collection .` before pushing a workflow change: the session's network proxy refuses the online requests of zizmor and pinact, which the workflow-lint job of the pull request makes. `workflow-lint.yml`, `scorecard.yml`, `.github/workflow-lint/` and `.github/scorecard/` are identical in all five BayanDocs repositories: change them in all of them together.

## Engine artifacts

Work package CORE-007 builds two artifacts for the shells, and drivers that test them the way a shell uses them:

- `cargo xtask sdk [--target <triple>]` builds the **C SDK** for the host (or the target) in `target/artifacts/bayan-core-sdk-<triple>/`: the static and the dynamic library, `include/bayan_ffi.h`, the protocol's JSON Schema, and the licence texts the binaries need, in the layout bayan-desktop's `src/engine/README.md` expects. `cargo xtask c-driver` compiles the C driver, `crates/bayan-ffi/c-driver/driver.c` (plain C11), against that SDK twice, linked statically and dynamically, and runs both; on Windows, run it from a Visual Studio developer environment.
- `cargo xtask wasm-package` builds the **WebAssembly package** in `target/artifacts/bayan-core-wasm/`: the engine module and wasm-bindgen's glue, the worker host `bayan-worker.js`, the protocol's JSON Schema and TypeScript declarations, the test page and the licence texts. It needs the `wasm-bindgen` tool at the version of the wasm-bindgen crate in `Cargo.lock`, which `scripts/dev-setup.sh` installs. It then reads the import section of the module it packages, `bayan_wasm_bg.wasm`, and fails on any import that `WASM_IMPORTS` in `xtask/src/artifacts.rs` does not list with what it does and why the engine needs it, and on any listed import that the module no longer has (`xtask/src/wasm_imports.rs`): in the browser every way out of the module, to a clock, randomness or anything else, is an import, and the engine never touches the outside world itself (ADR-0012 §5). Today the module imports three functions of wasm-bindgen's glue, which only move values between the module and its glue. A new import needs a reviewed change to the list, and one that reaches the outside world also an ADR that accepts it: ADR-0012's amendment of 2026-10-08 accepts Loro's randomness and clock, which will appear when bayan-crdt is linked into the engine. `node crates/bayan-wasm/js/tests/node-driver.mjs target/artifacts/bayan-core-wasm` runs the Node.js driver (Node.js 24, no npm packages), which runs the worker host in a worker thread that imitates a browser's. For the test page, serve the package folder over HTTP (for example `python3 -m http.server -d target/artifacts/bayan-core-wasm`) and open `test-page.html`.
- `cargo xtask miri` runs bayan-ffi's unit tests under Miri, on the nightly toolchain that `scripts/dev-setup.sh` installs with it.

Both drivers print `tile <digest>` for the same tile; `.github/workflows/artifacts.yml` builds the SDK on Linux x86-64, Windows x86-64 and macOS arm64 and the WebAssembly package on Linux, runs the C driver on every SDK and the Node.js driver on all three systems, checks that all six rendered the same tile (a driver job that failed or was skipped fails that check too), runs Miri, and uploads the SDKs and the package with SHA-256 checksums. It runs in the merge queue too (`merge_group`), so that `Same tile everywhere` and `Miri (bayan-ffi)` can be required checks of `main`'s ruleset (the architecture review of 2026-10-27, finding H1). Both drivers must leave standard error empty: they make the engine panic on purpose, and the engine prints nothing, panics included, because a message could quote document content. The workflow uses no cache: the artifacts are distributed, so they are built from a fresh checkout and fresh downloads, never from files a cache restored. Each artifact carries `THIRD-PARTY-LICENSES.txt`, the licences of the crates compiled into it (`xtask/src/notices.rs`, which fails on a crate without a licence file or with an Apache-2.0 NOTICE file), and the Rust standard library's notices.

Generated files are committed and checked by tests, so a change to the protocol's Rust types or to the C interface fails the gate until they are regenerated and reviewed: `BAYAN_UPDATE_GENERATED=1 cargo test -p bayan-engine --test engine` rewrites `crates/bayan-engine/protocol/engine-protocol.schema.json` and `engine-protocol.d.ts`, and `BAYAN_UPDATE_GENERATED=1 cargo test -p bayan-ffi --test header` rewrites `crates/bayan-ffi/include/bayan_ffi.h`. `bayan-cli protocol schema` and `bayan-cli protocol typescript` print the first two.

## Lint rules and exceptions

- Floating-point methods whose result is not exactly specified are forbidden in every crate, with no exceptions, because ADR-0005 §4 allows floating point only as exact IEEE-754 basic operations: platform math such as `sin`, `exp` and `powf`, whose results differ between platforms (use the deterministic functions in bayan-units); the `algebraic_*` methods, which let the compiler reorder or fuse operations (use the plain `+ - * / %` operators); and `min`, `max` and `clamp`, which may return `+0.0` or `-0.0` non-deterministically (compare explicitly, as in `if a > b { a } else { b }`). Arithmetic, `sqrt`, `mul_add`, rounding, sign and comparison methods are exact and allowed. The full list, with the reason for each, is in `clippy.toml`. The lint behind these bans, `clippy::disallowed_methods`, is set to `forbid`, so no code can make an exception: `#[expect]` or `#[allow]` of it, or of a group that contains it such as `clippy::style` or `clippy::all`, fails to compile with error E0453 when Clippy runs. (A plain `cargo build` does not run Clippy and does not notice; the gate's Clippy step does.)
- `HashMap` and `HashSet` are forbidden because their iteration order is random (ADR-0005 §5); use `BTreeMap` and `BTreeSet`.
- `unsafe` code is forbidden everywhere except bayan-ffi and bayan-wasm. There it is still denied by default and allowed only where `#[expect(unsafe_code, reason = "…")]` marks it, and every `unsafe` block needs a `// SAFETY:` comment (ADR-0006 §2).
- Engine code never prints, never calls `unwrap()` outside tests, and never exits the process; documented errors and panics, and explicit numeric conversions, are required. `Cargo.toml` explains each lint.
- Code that ships names none of the five modules of Rust's standard library that exist for the outside world (ADR-0012 §5, ADR-0005 §5, architecture §12): in every crate that `OUTSIDE_WORLD` in `xtask/src/verify.rs` does not list, it names none of `std::env`, `std::fs`, `std::net`, `std::process` and `std::time`, and a crate on the list uses only the modules that its entry names, with the reason. Ask the host for what the code needs instead (a time, the bytes of a file, a setting); for a length of time without a clock, use `core::time::Duration`, the same type as `std::time::Duration`. The engine's crates, bayan-wasm among them, are not on the list; bayan-ffi (the desktop host's clock of recordings, and its `abort`), the command-line tools, bayan-lab, the spikes and xtask are. After its runs, the Clippy step reads every line of the Rust files that the compiler compiled into each member's units that are not tests, as their dependency files list them (`xtask/src/outside_world.rs`). So tests that use these modules go into integration tests or into modules declared with `#[cfg(test)] mod name;` and written in a file of their own, which the compiler does not read for the code that ships; a test module written in place, `#[cfg(test)] mod tests { … }`, counts as code that ships, because a macro handed it could drop its condition. The check also reads the strings in attributes, decoded as the compiler decodes them, because a derive macro can make one code that ships (`#[serde(default = "std::process::id")]` calls that function); prose in an attribute, such as an `#[expect]`'s `reason`, is checked the same way, so name the modules there in words, not as paths, and never write `std` on its own. Documentation (`///`, `//!`, `#[doc …]`) is not read, because nothing compiles it into code that ships, and neither is a string that cannot be read as Rust at all. The check is not a lint: xtask reads the source text itself, so no attribute can switch it off, also not one that a macro assembles. It finds a module after `std::` whatever spaces, comments and raw identifiers stand between, also in `use` groups, and it rejects every way to name std that would let a later path reach the modules unseen: `std` on its own (renamed, handed to a macro, or used as a name), `std::*`, `self` in a group after `std::`, `std::` followed by a metavariable, a path in a macro from a metavariable into one of the five names or another metavariable, and a metavariable in a `use` or `extern crate` declaration (`$crate` is fine). It models paths rather than resolving names, so it cannot see a path that never writes the module's name, such as a dependency's re-export of a module of std under another name, and it reads only the workspace's own code, so it cannot see a dependency's function that reaches the outside world itself, such as cfb's `cfb::open(path)`. Nor does it see the other parts of std that reach the outside world: the methods of `std::path::Path` that ask the file system (`exists`, `metadata`, `read_dir`, `canonicalize` and others) and `std::hash::RandomState`, which seeds itself from the operating system. An attribute macro, or any procedural macro, can rewrite the code it is applied to; no workspace member is one, and the macros of dependencies are reviewed with them. So a pass means that the code names none of the five modules, not that it cannot reach the outside world; `xtask/src/outside_world.rs` lists these limits. In the preflight, a crate outside the list may not depend on one on the list except for its tests, and the list cannot go stale: an entry for a member that does not exist, or a module that the crate's code that ships no longer uses, fails.
- Never add a `clippy.toml` or `.clippy.toml` anywhere below the repository root, and never set the `CLIPPY_CONF_DIR` environment variable (also not in the `[env]` table of `.cargo/config.toml`). Clippy does not merge configuration files: for each crate it reads only the nearest one above the crate's folder, so such a file would replace the root `clippy.toml`, bans included, for every crate beneath it. Put every Clippy setting in the root `clippy.toml`; the gate rejects any other configuration.
- Never pass compiler flags that lower lint levels or unlock unstable features: `--cap-lints` (which lowers even `forbid`), `-A`/`--allow`, `--force-warn`, `-Z` options or `@file` arguments, through `RUSTFLAGS` and its relatives or `rustflags` in `.cargo/config.toml`, and never set `RUSTC_BOOTSTRAP`. The preflight rejects them. Other flags, such as `-C target-feature=…` for WebAssembly, are fine.
- Never run the compiler through a wrapper or a replacement program: no `RUSTC_WRAPPER`, `RUSTC_WORKSPACE_WRAPPER` or `RUSTC` (or their `CARGO_BUILD_…` forms), and no `rustc-wrapper`, `rustc-workspace-wrapper` or `rustc` in `[build]` of `.cargo/config.toml`. Such a program sees every compiler call and could weaken the lints for one chosen crate where nothing would notice, so the preflight rejects it. That includes compiler caches such as sccache; unset the variable while you run the gate.
- Choose configurations only with the approved conditions. In `#[cfg(…)]`, `cfg!(…)` and the first argument of `#[cfg_attr(…, …)]`, code may use only `test`, `debug_assertions` and `target_arch = "wasm32"`, combined with `all`, `any`, `not`, `true` and `false`; the Clippy step checks the code under every combination of their values, so nothing under them escapes Clippy. The preflight rejects every other condition, for example `feature = "…"`, `windows`, `unix`, `target_os = "…"`, any other `target_arch`, `clippy`, `miri`, `doc` or a name of your own: code under it would be compiled in a configuration that Clippy never checks, where none of the bans apply. Only the lint canary's crate may use its switch `bayan_lint_canary = "…"`. To approve another condition, add it to `APPROVED_CONDITIONS` in `xtask/src/verify.rs` with its reason, together with the Clippy runs in `CLIPPY_RUNS` that check the code with it both on and off, in a reviewed pull request; the unit test `the_clippy_runs_check_every_combination_of_the_approved_conditions` fails otherwise. Feature flags are not approved: make optional support, such as `serde`, unconditional, or approve `feature = "…"` together with Clippy runs that switch it on and off. Clippy checks the dev and release profiles; a work package that builds or ships with another profile adds it to `CLIPPY_RUNS`.
- Write every condition out in full. A condition may not contain a macro's metavariable (`$`), and the words `cfg` and `cfg_attr` may stand only directly before their condition (`cfg(`, `cfg!(` and `cfg_attr(`), so that no macro can build a condition from what it is handed: a `macro_rules!` matcher such as `$tool:ident :: $lint:ident`, handed the lint path `clippy::disallowed_methods`, could otherwise keep only `clippy` and write `#[cfg(not($tool))]`, and a macro handed the word `cfg` could write `#[$name(…)]`. Every other word that starts with `cfg` is rejected too, so never give anything a name that starts with `cfg`: `cfg_select!`, which the pinned toolchain offers, chooses code by conditions that are not written inside `cfg(…)`, and later Rust versions may add more such macros. Write `#[cfg(…)]` on the items instead, and `cfg!(…)` with round brackets.
- Never hide code from Clippy behind its own condition. Clippy sets the condition `clippy` when it compiles a crate and a normal build does not, so code under `#[cfg(not(clippy))]` would be compiled, tested and shipped but never linted. Besides rejecting it as a condition, the preflight rejects the bare identifier `clippy` (not followed by `::`) anywhere in the workspace's Rust files outside comments and strings: as an argument handed to a macro such as `m!(clippy)`, and as the name of a variable or function. Lint paths such as `clippy::unwrap_used` are fine; name things `clippy_config` or similar.
- Inside a macro, write every attribute out in full. A `macro_rules!` macro could write any attribute from what it is handed, such as `#[$attribute] mod sine;` handed `path = "…"`, so the preflight rejects an attribute that contains a metavariable anywhere outside the macro's matchers (the patterns its input must match). An attribute stays an attribute when its `#` and `[` are written apart, so the preflight also rejects the split forms found so far (the others pass the compiler but mean something else, so there is no reason to write them): a `#` must be written directly against the `[` or `![` it opens — a `#` that any other token follows is rejected, both in the code a macro writes (`# $attribute …`, which becomes `#[…]` when `$attribute` is a bracket group) and in what is handed to a macro (`m!(#, …)`, which hands it a bare `#`); and a `[…]` written directly after a metavariable (`$name [ … ]`), a repetition (`$( … )* [ … ]`), or either with a `!` between (`$name ![ … ]`) is read as an attribute, because the substitution before it could expand to `#` or `#!`. If a `[…]` after a metavariable is really an index, bind it first: `let index = $index; $array[index]`. The one exception passes on an attribute exactly as it was written where the macro is called, such as a doc comment, which the preflight checks there: bind it with `$(#[$meta:meta])*` in the matcher and write it as `$(#[$meta])*`, with the `#` against its bracket. Document the items a macro creates with doc comments where the macro is called, not with `#[doc = $text]`. These rules are a model of the compiler, and they do not catch every split form: a macro can keep the `#` of an attribute written in full where it is called, drop that attribute's bracket, and write the `#` before a bracket group handed in separately (`($hash:tt $dropped:tt, $bracket:tt) => { $hash $bracket mod hidden; }`, called as `m!(#[doc = "…"], [path = "…"])`, or without the comma), which builds a `#[path]` that the preflight does not see. The compiler's own record backs the rules for every form that makes the compiler read a file: the Clippy step compares the files that the compiler read with the files that the preflight read (see the next item), so such a `#[path]` fails there. Nor can a split form choose code: conditions are checked wherever `cfg` and `cfg_attr` stand, inside an attribute or not, and the bare identifier `clippy` is rejected anywhere. A split form can still write a lint attribute that neither the preflight nor Clippy sees: handed `[allow(clippy::disallowed_types)]`, it switches off the hash-map ban of ADR-0005 §5 for the item it precedes, because Clippy's `allow_attributes` lint, which rejects an `#[allow]` written out, does not report one that a macro assembles, and an `#[expect(…)]` passes the same way. That works for every lint that is not set to `forbid`, such as `clippy::unwrap_used`; only the forbidden ones, the float bans among them, cannot be lowered (error E0453). The lint audit at the end of the Clippy step catches such an exception, whatever wrote it (see "Every lint exception is written out in full, and the gate checks it" below), so reviewers need not check macros that take a `#` or a bracket group as a `tt` for lint attributes.
- Keep every Rust file where the gate reads it. The preflight reads every `.rs` file below the folders of the workspace members (it skips only the build folder `target/` at the root) and rejects what would make the compiler read any other file: `include!` (the identifier `include` anywhere outside comments and strings, so never name anything `include`; `include_str!` and `include_bytes!` read data and are fine); the attribute `#[path = "…"]`, also inside `cfg_attr` and, as far as the previous item reaches, from a macro's arguments; a symbolic link in a member's folder; a file named like `sine.RS`, which Windows and macOS also find as `sine.rs`; and a target whose root file lies outside its crate's folder or does not end in `.rs` (a path in `[lib]`, `[[bin]]`, `[[test]]`, `[[bench]]` or `[[example]]`, or `build = "…"`, moves it). Declare modules with a plain `mod name;` and keep their files where the compiler looks by default (`name.rs` or `name/mod.rs`). Never make a member depend by path on a crate that is not a workspace member, for example one in the excluded folder `fuzz/`: Cargo compiles such a crate without Clippy, and the preflight does not read it. `cargo xtask check-exact-pins`, in the gate's supply-chain step, rejects such a dependency, and `cargo xtask check-lockfile-age` rejects a crate that Cargo builds from a folder through `[patch]`, `[replace]` or `paths`. The compiler's record backs all of these rules: after each Clippy run, the Clippy step reads the dependency file that the compiler wrote for every unit of a workspace member, which lists every file the compiler read, and fails on any file that the preflight did not read, apart from Clippy's own two and the data files of `DATA_FILES` (next item), whatever route led the compiler to it.
- List every data file in `DATA_FILES`. A crate may read data with `include_str!` or `include_bytes!` (a test fixture, a committed font, or a workflow whose pins xtask's tests compare), but every file that the compiler reads and the preflight does not, which is every file other than the `.rs` files below the members' folders, must be listed in `DATA_FILES` in `xtask/src/verify.rs`, next to `BUILD_SCRIPTS` and `PROC_MACROS`, with the members that read it and the reason, in a reviewed pull request. A dependency file does not say whether a file was read as data or compiled as code, so reviewers check that every listed file is data, never Rust code. The Clippy step fails on an unlisted file, on a listed file that a member the entry does not name reads, and, so that the list cannot go stale, on an entry whose file a member it names read in none of the Clippy runs, an entry for a file that the preflight reads anyway, and an entry that names no member or one that does not exist. Clippy's own two files, the root `Cargo.toml` and `clippy.toml`, need no entry only under the exact names Clippy gives them (`Cargo.toml` relative to the compiler's working folder, which is the workspace root for members, and the absolute path that `std::fs::canonicalize` gives the root `clippy.toml`): named any other way, as by `#[path = "../../../Cargo.toml"]`, they count like any other file, because a file can be valid TOML and valid Rust at once. An absolute `#[path]` can name the root `clippy.toml` exactly as Clippy does, so a `clippy.toml` made valid Rust could pass on the one machine whose path it names; it cannot pass CI, whose three checkouts have different roots, and like the data files it is trusted by review. A crate that reads them itself, as xtask's tests do, lists them like any other data file.
- No crate has a build script (`build.rs`, or `build = "…"` in its manifest) unless `BUILD_SCRIPTS` in `xtask/src/verify.rs` lists it with a reason; the preflight rejects any other. A build script runs code during the build and can change how its crate is compiled, so a build script must never set Clippy or compiler variables through `cargo::rustc-env` (for example `CLIPPY_CONF_DIR`, which would switch off the root `clippy.toml` for that crate), and reviewers read every listed build script, and every change to one, in full.
- No crate is a procedural-macro crate (`proc-macro = true` in `[lib]`) unless `PROC_MACROS` in `xtask/src/verify.rs` lists it with a reason; the preflight rejects any other. A procedural macro runs code while the compiler compiles the crates that use it, and can produce any code, hidden conditions included, without that code appearing in a source file, so the source check cannot see what it writes. Reviewers read every listed macro, and every change to one, in full. Both lists start empty, and the preflight also rejects an entry that names no workspace member or a member without such a target, so they cannot go stale. Procedural macros from dependencies, such as serde's derive, are not affected; they are reviewed with the dependency (ADR-0017).
- The only way to make an exception is `#[expect(lint_name, reason = "why this is safe")]` on the smallest item that needs it. `#[allow]`, and exceptions without a reason, are rejected; an `#[expect]` that is no longer needed fails the build, so exceptions cannot go stale. Clippy's own hint to "add `#[allow(…)]`" does not apply here. The float-method bans have no exceptions, because ADR-0005 §4 allows none, and the compiler enforces that (see the first item). `#[expect(clippy::disallowed_types, reason = "…")]` is only for a hash map or set whose iteration order cannot affect any output, and the reason must say why.
- Every lint exception is written out in full, and the gate checks it. Clippy's `allow_attributes` lints see only attributes written in the source, so the lint audit at the end of the Clippy step (`xtask/src/lint_audit/`, CORE-009) compiles the workspace again with every guarded lint force-warned (step 3) and fails on every occurrence that an attribute silences but that no `#[expect(<lint>, reason = "…")]` or `#![expect(<lint>, reason = "…")]` written out in full in the source covers, naming exactly that lint: an exception for a group such as `clippy::all` does not count, and one inside `cfg_attr` counts only in the units where its condition holds. It does not matter what wrote the attribute that silences the occurrence: a macro of the workspace that assembles it from tokens handed in separately, a macro of another crate that puts out an `#[allow]` written inside its input (such as std's `thread_local!`), or a procedural macro. Its model of the code that an exception covers may be stricter than the compiler, never looser, so where it cannot tell how far the compiler applies an exception, the exception covers nothing in the model. An `#[expect]` covers what it stands before, together with that item's built-in attributes such as `#[unsafe(no_mangle)]` (not a derive, whose code is an item of its own, nor `#[test]`, `#[should_panic]`, `#[ignore]` or `#[cfg]`): in item or statement position, an item or `let` statement up to its first `;` or the end of its first `{…}` group; on another statement, a field or a variant in the definition of a struct, union or enum, or a match arm, also no further than its first `,` or a `>` that is not part of `->` or `=>`; on a parameter of a function or a closure, only the parameter's pattern, never its type or a closure's body, which the compiler does not cover either. It covers nothing on a generic parameter (the compiler covers neither its bounds nor its default, and not even its name for the lints of its later passes), on a field of a struct expression or pattern (which look alike, and on a pattern's field the compiler applies it to almost nothing), on a parameter of a function pointer type, on the first statement of a block whose `{` the model cannot tell from a struct expression's, such as after `if x`, inside a macro's input, because the macro decides where it and the tokens after it go, and anywhere else that the model does not recognise: write it on the enclosing item or statement instead. One on `mod name;` covers the module's file and its submodules', and an `#![expect]` the rest of its block or module, and in a crate's root file the whole crate. One on a `macro_rules!` definition or on a macro call covers nothing, because the compiler does not apply it where the macro expands. Code that a macro writes is covered by an `#[expect]` next to it in the macro's own code, up to a metavariable that could end the item (any but `$crate` and those bound as `ident`, `lifetime`, `literal`, `vis`, `ty`, `path`, `expr`, `pat` or `meta`), or by an exception around the place where the macro is called. The compiler reports such code at the macro's own code, the same place for every call, so each call is checked on its own, and the audit names the place of the call that no exception covers. When the audit reports an occurrence that a written exception does cover, the model counts that exception for less than the compiler does: move the `#[expect]` onto the enclosing item or statement, as above; never stop force-warning a lint. Occurrences of a lint that the member's lint table switches off, such as `manual_clamp`, are not judged: an `allow` entry switches a lint off only at a higher priority than every group that the table sets to `warn`, `deny` or `forbid` (the groups that rustc, Clippy and rustdoc list in their own `-W help`), because Cargo passes the entries in the order of their priority and the last one that names the lint or a group that holds it wins; and an occurrence in a file that the source check does not read fails, because no exception written in the workspace can cover it. What the audit does not see: attributes that change linting without setting a level, such as `#[automatically_derived]` or `#[clippy::msrv]`; code that a lint's own implementation skips, such as most code in the expansion of another crate's macro, which no run reports; where tokens that a derive or an attribute macro copies from its input into a separate item come from: they are judged where they are written, so an `#[expect]` on the input item counts for them, although the compiler applies it to that item only, which is accepted because the exception is written over that very text; and the lints it cannot force-warn: the `warnings` group, which the compiler refuses (error E0602), and the lints of its skip list (`UNGUARDED` in `xtask/src/lint_audit/guarded.rs`), five unstable lints that the pinned compiler calls unknown. The list cannot go stale: the step fails when the compiler calls a force-warned lint unknown that the list does not hold, and when force-warning a listed lint no longer fails for the reason the list gives. A new toolchain can therefore change the list, in the monthly dependency session.

## Adding a crate

1. Create `crates/<name>/` with a `Cargo.toml` like the existing crates' (every `[package]` field taken from the workspace, plus `[lints]` with `workspace = true`), and make sure the crate is in the crate map of `docs/plan/03-architecture.md`.
2. Start `src/lib.rs` with crate documentation that states the crate's responsibility, its layer and the layering rule (copy the wording of an existing crate), followed by `#![forbid(unsafe_code)]`.
3. Depend only on crates of the same layer or below. Declare third-party dependencies once in `[workspace.dependencies]` of the root `Cargo.toml`, with an exact `=x.y.z` version, and justify each in the pull request (ADR-0017).
4. If the crate cannot run in a browser, such as a command-line tool, add it to `NATIVE_ONLY` in `xtask/src/verify.rs` with the reason; otherwise the gate builds it for WebAssembly, and Clippy checks it there too.
5. Avoid a build script, and do not make the crate a procedural-macro crate. If the crate really needs either, add it to `BUILD_SCRIPTS` or `PROC_MACROS` in `xtask/src/verify.rs` with the reason (see "Lint rules and exceptions").
6. Use only the approved conditions (`test`, `debug_assertions` and `target_arch = "wasm32"`), written out in full. If the crate needs another, such as a feature flag, approve it first, together with the Clippy runs that check it (see "Lint rules and exceptions").
7. If the crate reads data with `include_str!` or `include_bytes!`, such as test fixtures, list each file in `DATA_FILES` in `xtask/src/verify.rs`, with the crate and the reason (see "Lint rules and exceptions").
8. Keep the crate's code that ships away from `std::env`, `std::fs`, `std::net`, `std::process` and `std::time`; get time, files and settings from the host, and use `core::time::Duration` for lengths of time. Tests that need these modules go into integration tests or into a test module in a file of its own (`#[cfg(test)] mod tests;`), never into one written in place. A tool or spike that needs them goes on `OUTSIDE_WORLD` in `xtask/src/verify.rs`, with the modules it uses and the reason (see "Lint rules and exceptions").
9. Run `cargo xtask verify`.

Spike and Fidelity Lab crates live in `spikes/` and `lab/` and are added to `members` in the root `Cargo.toml` by name; see the READMEs there.

## Toolchain

Rust is pinned to 1.99.0 (released 2026-10-01) in `rust-toolchain.toml`, with the targets wasm32-unknown-unknown (the web app's engine) and wasm32-wasip1 (the tests in WebAssembly); rustup installs a missing target by itself on first use, or `scripts/dev-setup.sh` does it ahead of time. The version is also the minimum supported version (`rust-version` in `Cargo.toml`, ADR-0006 §7). Change it only in the monthly dependency session, to the newest stable release that is at least 24 hours old, in three places at once: `rust-toolchain.toml`, `rust-version` in `Cargo.toml` (the gate checks that they are equal), and `RUST_STABLE` in the docs repository's `scripts/cloud-environment-setup.sh`. Rust 1.100 (2026-11-12) is the first release that enforces `global-min-publish-age`; adopt it in the first session after it is 24 hours old.

## Dependency mechanisms

Exact `=x.y.z` requirements in `[workspace.dependencies]`, which `cargo xtask check-exact-pins` checks together with every member's dependencies; `Cargo.lock` committed and every build runs with `--locked`; `.cargo/config.toml` sets `global-min-publish-age = "1 day"`, which Cargo enforces from Rust 1.100, and only when it resolves new versions. `cargo xtask check-lockfile-age` therefore checks every package version that a pull request adds to a `Cargo.lock`, the main workspace's or `fuzz/Cargo.lock`: it reads the publish time from the crates.io sparse index (`pubtime`), or from the crates.io API (`created_at`, at most one request per second) for a version without one, sends a User-Agent that names the tool and this repository, and fails if the version was published less than 24 hours before the commit that added it, or before now, or if its checksum in `Cargo.lock` is not the one crates.io published. Before that it makes sure that each `Cargo.lock` is what Cargo builds: the packages `cargo metadata --all-features` resolves must be exactly those of the `Cargo.lock`, no package outside the workspace may be built from a folder (`[patch]`, `[replace]`, `paths`, vendored sources) except, in the fuzz workspace, the members of the main workspace that it depends on by path, and the file must be in the exact layout Cargo writes. Both checks find the workspaces by the `Cargo.lock` files that Git tracks (bayan-core#22), so a new workspace with a lockfile of its own is checked from the commit that adds it, without being listed anywhere. Three guards make them fail instead of passing over what they cannot see: a `Cargo.lock` that Cargo would not use (in a folder that is not the root of a workspace), a file named like `Cargo.lock` in another letter case, and a `Cargo.toml` that Git tracks outside every checked workspace (a workspace whose `Cargo.lock` is not committed, or a package in a folder that a workspace excludes), which Cargo could build from a lockfile that no check has seen; commit its `Cargo.lock`, make it a member of a checked workspace, or remove it. A package that the change adds from a Git repository fails too: it has no crates.io publish time or checksum to check. Its code, in `xtask/src/supply_chain/`, is identical in bayan-server; its tests replay recorded crates.io answers (`xtask/src/supply_chain/fixtures/`), so they never use the network. `cargo deny check` runs in the gate on every pull request and every night with `deny.toml`: RustSec advisories (unmaintained and unsound crates anywhere in the build, and yanked versions, fail), the ADR-0017 license allowlist, duplicate versions as warnings, and crates.io as the only source; a Git dependency would need an `allow-git` entry and a fixed `tag` or `rev`, and `cargo xtask check-lockfile-age` refuses every package from a Git repository that a change adds, because it cannot judge a commit's age yet (the work package that needs a Git dependency teaches it first). `deny.toml` ignores six advisories, each with its reason, all for crates that Loro (ADR-0008) depends on and none with a fixed version, accepted by the owner on 2026-10-08 (ADR-0008, amendment 2026-10-08; `spikes/crdt-model/REPORT.md` §10): four say that im, sized-chunks, bitmaps and atomic-polyfill are unmaintained, and two that im and sized-chunks are unsound in code that Loro does not reach. Every monthly dependency session re-checks them (the docs repository's `developer/dependency-update-runbook.md`): each reason must still hold, and each is removed as soon as Loro no longer needs its crate (Loro is asked to move to the maintained replacements, imbl and imbl-sized-chunks); every other advisory fails the gate. The supply-chain workflow (`.github/workflows/supply-chain.yml`, the same in every BayanDocs repository) fails on update-bot configuration and runs pip-audit on the hash-pinned Python tool requirements, on every pull request and nightly. Tools used in CI are pinned and checksum-verified: cargo-deny 0.20.2 in `.github/workflows/verify.yml`, matched by `CARGO_DENY_VERSION` in `xtask/src/verify.rs` (a test keeps them equal); Node.js 24.22.1 in the same workflow and in `scripts/dev-setup.sh`, matched by `NODE_VERSION` in `xtask/src/verify.rs` (a test keeps them and the copies in `.github/workflows/artifacts.yml` and `.github/workflows/text-pipeline.yml` equal), checked against the SHA-256 checksums of nodejs.org's signed `SHASUMS256.txt`; GitHub Actions are pinned to full commit SHAs; the workflow-lint job checks each pin and its age, and the tools that the workflow-lint, Scorecard and CodeQL workflows download (zizmor, pinact, Scorecard and the CodeQL bundle) are pinned by version and SHA-256 (see "Workflow conventions"). xtask itself has no dependencies. Routine upgrades happen only in the monthly dependency session, following the docs repository's `developer/dependency-update-runbook.md`.
