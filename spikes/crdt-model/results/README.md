# CORE-004 raw results

The measurements behind `../REPORT.md`, as the programs printed them (`metric <name> <value> <unit>` lines, or the drivers' own lines). Every file starts with `#` lines that give the command, the commit, the date and, for WebAssembly, the Node.js version. All were taken on 2026-10-08, after the review of the first version, on one machine: 4 virtual CPUs (Intel Xeon @ 2.10 GHz), 15 GiB RAM, Linux 6.18, with Rust 1.99.0 and Node.js 24.21.0. Paths are shortened to `<data>` (the folder of the generated snapshots), `<repository>` and `target`.

| Files | What | Produced by |
|---|---|---|
| `generate-full.txt`, `generate-subset.txt` | Building the synthetic 500-page documents: size, content counts, the view's checks | `crdt-model generate --mode full\|subset --out <file>` |
| `generate-small-native.txt`, `generate-small-wasm.txt` | The 10-page document generated natively and in WebAssembly: same content, different snapshot bytes (report §5.4) | `crdt-model generate --mode full --small --out <file>`, and the same under `run-wasi.mjs` |
| `snapshot-gzip-sizes.txt` | How much gzip shrinks the generated snapshots | `gzip -9 -c <file> \| wc -c` |
| `native-full-{1,2,3}.txt`, `native-subset-{1,2,3}.txt` | Benchmarks, native x86-64 release build, unmodified Loro 1.16.2 | `crdt-model bench --mode full\|subset --snapshot <file>` |
| `wasm-full-{1,2,3}.txt`, `wasm-subset-{1,2,3}.txt` | The same in WebAssembly (`wasm32-wasip1` under Node.js), unmodified Loro | `node run-wasi.mjs <module> <data> bench --mode … --snapshot /data/<file>` |
| `native-full-shallow-{1,2,3}.txt` | The full-model benchmark opened from the shallow snapshot (old history trimmed) instead of the full one, natively (report §7, F11) | `crdt-model bench --mode full --snapshot <file>.shallow` |
| `native-patched-loro-*.txt`, `wasm-patched-loro-*.txt` | The same with Loro's quadratic rich-text decoding fixed (report §7, F1): a copy of `loro-internal` 1.16.2 with the three lines of `loro-f1-fix.patch`, used through `[patch.crates-io]` in a scratch copy of the workspace with a target folder of its own. Measured to show the effect of the fix; nothing in the repository uses the patched copy. | as above |
| `loro-f1-fix.patch` | That change, and how the scratch copy used it | — |
| `profile-*.txt` | Excerpts of callgrind profiles (inclusive instruction counts) that explain the performance figures: the first read after loading, the first update after opening (from the full and from the shallow snapshot), 1,000 concurrent edits and 20 undo steps, each collected only inside one call of the benchmark's `profile_*` function, on the build with the F1 fix; and the first read on unmodified Loro, which shows F1 itself | `valgrind --tool=callgrind --collect-atstart=no '--toggle-collect=*profile_<phase>*' crdt-model bench --mode full --snapshot <file>` |
| `normalization-100000.txt` | The normalization property test with 100,000 randomly broken documents | `BAYAN_NORMALIZATION_CASES=100000 cargo test --release --locked -p bayan-model --test normalization -- --nocapture` |
| `converge-1000x10000.log` | The full convergence run of the brief: one line per run, then a summary. **Until the re-run on commit f1331c4 finishes, this file is still the first version's run** (2026-10-07, on the code before the review, in two parts with a combined summary computed afterwards); the re-run replaces it. | `crdt-model converge --runs 1000 --operations 10000 --threads 4` |
| `fuzz-supervise-4500s.log` | The 75-minute fuzzing run (two workers, each restarted after an abort), with the panic sites and aborts it found and the CPU time it used | `crdt-model supervise --seconds 4500 --workers 2 --out <private folder>` |
| `minimized-findings.txt` | The findings of the first fuzzing runs after minimization, without their bytes (report §8.2) | `crdt-model minimize` |

The benchmarks and the normalization test ran one after another on the otherwise idle machine; the convergence run, the fuzzing run and the profiles ran afterwards, partly in parallel, so their run times are longer than on an idle machine (instruction counts do not depend on the load). The benchmarks, the profiles, the normalization test and the fuzzing run are from commit 50dbc7a; the convergence run is from commit f1331c4. The two commits in between change only how the simulation chooses the targets of its operations and how the materialization check, which only the simulation switches on, reuses the normalization it already computes (report §3, AC-1); the benchmarked operations do the same work, minus an empty commit. The generated documents, the benchmarks' counts, the profiles' instruction counts and the convergence run repeat exactly from their fixed seeds; timings vary with the machine, and a time-bounded fuzzing run stops at a different input each time.

The Automerge comparison's results are in `../../crdt-model-automerge/results/`, with the same kind of header.
