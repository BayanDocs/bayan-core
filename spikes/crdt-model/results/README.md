# CORE-004 raw results

The measurements behind `../REPORT.md`, as the programs printed them (`metric <name> <value> <unit>` lines, or the drivers' own lines). Every file starts with `#` lines that give the command, the commit, the date and, for WebAssembly, the Node.js version. All were taken on 2026-10-08, after the review of the first version, except `minimized-findings.txt` (2026-10-07, the first version's findings) and the convergence runs, which ended on 2026-10-09, on one machine: 4 virtual CPUs (Intel Xeon @ 2.10 GHz), 15 GiB RAM, Linux 6.18, with Rust 1.99.0 and Node.js 24.21.0. Paths are shortened to `<data>` (the folder of the generated snapshots), `<repository>` and `target`.

| Files | What | Produced by |
|---|---|---|
| `generate-full.txt`, `generate-subset.txt` | Building the synthetic 500-page documents: size, content counts, the view's checks | `crdt-model generate --mode full\|subset --out <file>` |
| `generate-small-native.txt`, `generate-small-wasm.txt` | The 10-page document generated natively and in WebAssembly: same content, different snapshot bytes (report §5.4) | `crdt-model generate --mode full --small --out <file>`, and the same under `run-wasi.mjs` |
| `snapshot-gzip-sizes.txt` | How much gzip shrinks the generated snapshots | `gzip -9 -c <file> \| wc -c` |
| `native-full-{1,2,3}.txt`, `native-subset-{1,2,3}.txt` | Benchmarks, native x86-64 release build, unmodified Loro 1.16.2 | `crdt-model bench --mode full\|subset --snapshot <file>` |
| `wasm-full-{1,2,3}.txt`, `wasm-subset-{1,2,3}.txt` | The same in WebAssembly (`wasm32-wasip1` under Node.js), unmodified Loro | `node run-wasi.mjs <module> <data> bench --mode … --snapshot /data/<file>` |
| `native-full-shallow-{1,2,3}.txt` | The full-model benchmark opened from the shallow snapshot (old history trimmed) instead of the full one, natively (report §7, F11) | `crdt-model bench --mode full --snapshot <file>.shallow` |
| `native-patched-loro-*.txt`, `wasm-patched-loro-*.txt` | The same with Loro's quadratic rich-text decoding fixed (report §7, F1): a copy of `loro-internal` 1.16.2 with the three lines of `loro-f1-fix.patch`, used through `[patch.crates-io]` in a scratch copy of the workspace with a target folder of its own. Measured to show the effect of the fix; nothing in the repository uses the patched copy. | as above |
| `loro-f1-fix.patch` | That change, and how the scratch copy used it | — |
| `profile-*.txt` | Excerpts of callgrind profiles (inclusive instruction counts) that explain the performance figures: the first read after loading, the first update after opening (from the full and from the shallow snapshot), 1,000 concurrent edits and 20 undo steps, each collected only inside one call of the benchmark's `profile_*` function, on the build with the F1 fix; and the first read on unmodified Loro, which shows F1 itself | `valgrind --tool=callgrind --collect-atstart=no '--toggle-collect=*profile_<phase>*' crdt-model bench --mode full --snapshot <file>` |
| `normalization-100000.txt` | The normalization property test with 100,000 randomly broken documents | `BAYAN_NORMALIZATION_CASES=100000 cargo test --release --locked -p bayan-model --test normalization -- --nocapture` |
| `converge-1000x10000.log` | The full convergence run of the brief on commit f1331c4, the code after the first review round (2026-10-08 to 2026-10-09): one line per run, sorted by run number, then the third part's summary and the combined one. It ran in three parts because the container restarted twice; the header says how they fit together, and that every operation the adapter refused was replayed and traced to the column bug that the final code fixes (report §3, AC-1). The first version's run (2026-10-07) is in the Git history of this file. | `crdt-model converge --runs 1000 --operations 10000 --threads 4` |
| `converge-100x10000-final-code.log` | The confirmation run on the final code: the full run's first 100 seeds on commit 6b71180, after the second review round, the reviewer's final check and the check of its fixes, where a run also fails if any action leaves writes pending (report §3, AC-1). The earlier confirmation runs on af24393 and 2672529 are in this file's Git history. | `crdt-model converge --runs 100 --operations 10000 --threads 4` |
| `fuzz-supervise-4500s.log` | The 75-minute fuzzing run (two workers, each restarted after an abort), with the panic sites and aborts it found and the CPU time it used | `crdt-model supervise --seconds 4500 --workers 2 --out <private folder in memory>` |
| `fuzz-supervise-4500s-on-disk.log` | An earlier attempt at that run with the output folder on the disk, kept for its CPU time: writing every input to the disk before importing it held each worker to about a fifth of a CPU (report §8.2) | the same, with `--out <private folder on the disk>` |
| `f5-stack-thresholds.txt` | How deeply nested a value may be before importing it overflows the stack, in release and debug builds, on 2 MiB and 8 MiB stacks (report F5, §6 Q7) | a scratch probe, not committed, that builds the update as `hostile_update` in `crates/bayan-crdt/tests/adapter.rs` does (the header describes it) |
| `f13-overlapping-marks.txt` | The time and memory of importing an update with many overlapping comment highlights, with and without a subscriber (report F13) | a scratch generator, not committed (a denial-of-service reproduction; the header describes it) |
| `minimized-findings.txt` | The findings of the first fuzzing runs after minimization, without their bytes (report §8.2) | `crdt-model minimize` |

The benchmarks and the normalization test ran one after another on the otherwise idle machine; the convergence run, the fuzzing run and the profiles ran afterwards, partly in parallel, so their run times are longer than on an idle machine (instruction counts do not depend on the load). The benchmarks, the profiles, the normalization test and the fuzzing runs are from commit 50dbc7a; the full convergence run is from commit f1331c4, the F5 and F13 measurements from d64ec12, and the confirmation run on the final code from 6b71180 (later commits change only documents). The two commits in between change only how the simulation chooses the targets of its operations and how the materialization check, which only the simulation switches on, reuses the normalization it already computes (report §3, AC-1); the benchmarked operations do the same work, minus an empty commit. The generated documents, the benchmarks' counts, the profiles' instruction counts and the convergence run repeat exactly from their fixed seeds; timings vary with the machine, and a time-bounded fuzzing run stops at a different input each time.

The Automerge comparison's results are in `../../crdt-model-automerge/results/`, with the same kind of header.
