# CORE-004 report: the Word-shaped document model on Loro

- **Work package:** [CORE-004](https://github.com/BayanDocs/docs/blob/HEAD/workpackages/phase-0/CORE-004-spike-crdt-document-model.md), the validation gate of ADR-0007 (the document model) and ADR-0008 (Loro behind the `bayan-crdt` adapter).
- **Date:** 2026-10-07; revised 2026-10-08 after the review of the first version (the pull request's "Changes since the review" maps each review item to its commit). **Loro** 1.16.2, **Automerge** 0.12.0, Rust 1.99.0, Node.js 24.21.0.
- **Measurements:** every figure in this report was measured on 2026-10-08 on the code of this revision (the convergence runs ended on 2026-10-09), except those marked as the first version's (2026-10-07: AC-1's first run, §8.2's earlier runs and `results/minimized-findings.txt`): commit 50dbc7a for the benchmarks, profiles, normalization test and fuzzing, f1331c4 for the full convergence run, d64ec12 for the F5 and F13 measurements, and 2672529 for the confirmation run on the final code (later commits change only documents). The second review round and the convergence runs then changed the model (§2), which is why the final code has a convergence run of its own (§3, AC-1). The two commits in between change only how the simulation chooses its targets and how the materialization check that only the simulation switches on reuses the normalization it already computes (§3, AC-1); the benchmarked operations do the same work as on 50dbc7a, minus an empty commit. Every file in `results/` names its command, commit, date and Node.js version. Machine: 4 virtual CPUs (Intel Xeon @ 2.10 GHz), 15 GiB RAM, Linux 6.18. Absolute times on a typical laptop will be lower; the ratios between configurations are what matter.

## 1. Summary and recommendation

**The model shape (ADR-0007) works.** Stories of atoms, with paragraph ends, field delimiters, anchors and table blocks as characters, merge correctly under heavy concurrent editing: in the full randomized run of the brief (1,000 runs of 10,000 operations on three replicas, with partitions, out-of-order delivery, undo and redo), every run of the first version ended with identical views satisfying I1–I7, and so did all 1,000 runs of the re-run on the reviewed code, which also checks every materialization and a fresh replica loaded from each final snapshot, and 100 runs on the final code, which also check that no operation leaves writes pending (§3, AC-1). Normalization is deterministic and idempotent and yields a valid view for 100,000 randomized broken documents, and the invariant checker that judges it now has a test for each invariant. The review found operations that, on their own, broke invariants in the stored state, and one that lost text (a refused move still deleted its source); every operation now checks everything before it writes anything, and refuses, until a Word Behavior Note says what Word does, edits that would split a field or a range (§2). A second review round found three more gaps, now fixed: values that another replica stored and the adapter cannot store made a split, a move or a materialization fail halfway; after concurrent moves duplicated a field or a bookmark, the check for whole fields refused every edit of either copy; and a move could put a table or a comment reference into a story nested inside it, or a table in the middle of a paragraph (§2). The convergence runs on the reviewed code then found a fourth: deleting a column failed halfway in a table whose stored state lists a row twice, which two replicas that delete the same row and both undo produce; every run now fails if an operation leaves writes pending (§2, §3). The reviewer's final check found the last two: an entry that another replica stored where a paragraph's property map belongs could still make formatting or materialization fail halfway, and a cell that a row's list holds twice made the column operations count columns as stored rather than as the view shows them; both are fixed (§2). One way for an operation to fail halfway remains, recorded for CORE-101: a replica that predicts this replica's next identifiers (§11). Nothing found suggests that the model shape is wrong. Preserved atoms (PreservedInline) were not modelled; they map like object anchors, which were (§9). The spike adds normalization rules N8 and N9, extends N5 and I5 to comment highlights, clarifies N3 and N7, and settles the mapping details (§9), which the docs pull request proposes.

**Loro (ADR-0008) is the right library, but not yet a safe one.** I recommended confirming ADR-0008 with three conditions, and the owner did so on 2026-10-08 (§10), because Automerge 3, the alternative, is worse on almost every measure (§5.3: compared with Loro carrying the small fix below, Automerge loads and reads 6.5 to 8 times slower, needs 5 times the memory, applies a 1,000-edit update 18 to 22 times slower, and spends about 0.4 s natively on every update however small; its snapshots are five times smaller, and its update for a whole session 14% smaller):

1. **A small upstream fix for loading.** Loro 1.16.2 decodes rich text from a snapshot in quadratic time: opening and showing the 500-page document takes 2.6 s natively and 7.0 s in WebAssembly, against targets of 0.3 s and 1 s. With the fix (§7, F1) it takes 0.51 s and 0.76 s: the WebAssembly target is met, the native one missed by 1.7×, because reading one Loro container per paragraph is costly (§5.2). The owner has since relaxed the native target to 0.6 s for now, which the fixed figure meets (§10, question 2).
2. **Hostile updates must not crash the engine.** Fuzzing found that crafted updates make Loro panic at 25 places and request absurd amounts of memory (an allocation failure aborts the process); values nested deeply on purpose overflow the stack (F5, measured with the adapter tests' generator, not found by fuzzing); and many overlapping comment highlights make an import slow (F13). All of it happens inside Loro's own decoding and applying, which runs before the adapter can look at the values; only the size limit is checked before any decoding, while the change and operation limits rely on Loro decoding the whole blob. The adapter contains panics (the poisoned replica refuses everything afterwards) and refuses values nested too deeply when they survive decoding; allocation failures and stack overflows can only be survived by isolating imports and restarting the engine, and slow imports need a time budget there (§8.3). The fuzzer that found these is committed and regenerates them from its fixed seeds within minutes, so they are effectively public: reporting them to Loro's maintainers privately is urgent (§7, question 5).
3. **Performance items for the model and storage work packages:** the first update after opening a document pays a one-time cost (58 ms natively and 95 ms in WebAssembly for 1,000 operations, against a target of 50 ms; later updates of that size take 8 ms and 13 ms), one undo step takes about 0.2 s in a 500-page document because Loro replays the story's whole history, reading one Loro map per entity is the largest part of the first read, and a document opened from a shallow snapshot pays about 0.2 s for every concurrent keystroke it imports (§5, F11).

**The owner's decisions** (2026-10-08, details in §10, recorded as dated amendments of ADR-0008, ADR-0012 and ADR-0017 in the docs pull request): Loro is confirmed on these three conditions; the native load target is relaxed to 600 ms for now (WebAssembly stays at 1 s); libFuzzer's licence (NCSA) is allowed for fuzzing dependencies that never ship; the six advisory exceptions for crates that Loro depends on are accepted, and every monthly dependency session re-checks them until Loro moves to maintained replacements; Loro's own calls to the platform's random-number generator and clock are a temporary exception to ADR-0012 until Loro lets the host supply them; and the owner sends the upstream reports, the crash findings privately ([BayanDocs/bayan-core#14](https://github.com/BayanDocs/bayan-core/issues/14)).

The WebAssembly benchmarks and tests need the `wasm32-wasip1` target, which `rust-toolchain.toml` lists since CORE-002, so rustup installs it by itself; this work package no longer changes `scripts/dev-setup.sh`.

**Operations** (all from the brief, plus moving a range, inserting objects and bookmarks): insert text, delete a range, format and clear formatting, split and merge paragraphs, set paragraph properties, insert a table, insert, delete and move rows, insert and delete columns, add a comment over a range, insert a field, insert an object, insert a bookmark, move a range (cut and paste). Each operation is one transaction: one commit, one undo step, one change that other replicas receive. Because Loro cannot abort a transaction, each operation checks everything that can refuse it before it writes anything: a refused operation changes nothing, except that it may first write structure the view already shows (materialization, which leaves the view unchanged). Operations refuse what Word refuses (typing after the final paragraph end, a table in the middle of a paragraph, also by a move, and content inside a story nested in it, such as a table in its own cell or a comment reference in its own comment), and, until a Word Behavior Note says what Word does (ADR-0007 decision 6, a follow-up), what would leave the stored state unbalanced or misplaced: deleting or moving part of a field or only one end of a range, and a comment reference, a range start or moved content at the block position before a table. Formatting refuses the atom binding's key and keys that name no mark of the model (a family name alone is no key, except `link`), and an operation refuses a value the adapter cannot store before it writes anything. Values that another replica stored and the adapter cannot store (a floating-point number, a container reference, a value nested too deeply) read as missing, in properties as in marks, and are never copied, so a split, a move or a materialization cannot fail halfway on them (second review round). A table row that the stored state lists twice (two replicas delete the same row and both undo, and each undo inserts it again) is shown once (N7) and changed once by the column operations; before, deleting a column deleted its cell twice and then failed with its deletions written, which left them for the next edit's undo step (found by the convergence runs, §3). Likewise a cell that a row's list holds twice (two replicas delete the same column and both undo) counts once: the column operations count columns as the view shows them, and deleting a column deletes every copy of its cell. An entry that another replica stored where a paragraph's property map belongs is written into when it is a map, created by other means than the adapter's, and left out when it is not (the view does not show that paragraph end, N5); and the identifiers that normalization derives for virtual paragraph ends (N1, N4) avoid every identifier that the stored state takes, so materialization only ever creates a new map, with exactly the properties the view shows (the reviewer's final check). One way for an operation to fail after writing remains: entity identifiers come from a generator that is not cryptographic, so a replica that has seen some of this replica's identifiers can compute its next ones and store a value under one first, and creating that entity then fails after the operation's earlier writes (§11). The benchmark's script of 1,000 random edits contains one deletion that would split a field, which is now refused.

**Tests:** bayan-crdt has 4 unit tests, 18 adapter tests and 3 panic-containment tests; bayan-model has 9 unit tests, 48 model tests (operations, undo, mark expansion, and values and entries that another replica stored and the adapter cannot store or did not create), 22 invariant tests (each builds a view that breaks exactly one check of the checker and checks that it is reported), 11 normalization tests (one of them the property test over random broken documents; two also time eight times their input, so that quadratic work fails them, one of them for fields nested in codes and in results), the convergence test (6 runs of 400 operations in CI, compared with the same plans on one replica alone) and a golden test that pins the outcome of a fixed simulation run (`tests/determinism.rs`); the spike crates have 10. `cargo xtask verify` runs them all natively and in WebAssembly (wasm32-wasip1 under Node.js), except one adapter test and the three panic-containment tests, which need threads or unwinding and run on the host only.

### 5.2 Why the targets are missed

**Load (F1, a Loro bug).** 92% of the native first read on unmodified Loro is spent in Loro's rich-text snapshot decoder (`decode_snapshot_fast`), almost all of it counting characters (`str::count::do_count_chars`, 91.8% of the read's instructions; `results/profile-first-read-unpatched.txt`). The cause is Loro's rich-text snapshot decoder, which, for every span of text, counts the characters of the *entire remaining text* to validate the span's length (`loro-internal` `src/state/richtext_state.rs`, `decode_snapshot_fast`). That is quadratic in the length of a story: about 2·10¹⁰ character visits for the 1.5-million-character main story. Counting once and subtracting each span's length (three lines, §7 F1) removes it: reading the raw state takes 369 ms instead of 2,454 ms natively, and 521 ms instead of 6,746 ms in WebAssembly. Releases 1.13.9 through 1.16.2 all contain the check, so no available version avoids it.

**Load, after the fix (our mapping).** The remaining 481 ms of the native first read split as follows (`results/profile-first-read.txt`, instruction counts of one call of the first read, on the build with the fix): reading the property maps of about 27,000 entities 38% (fetching each entity's container from the snapshot's key-value store and decoding it 21%, reading its values 16%; recognizing Loro's mergeable-container markers in the values, a parse and a CRC-24 per value, is about 10% of the whole), turning the 6,001 rich-text stories into runs 37%, and normalization 15%; allocating and freeing memory, spread over all of these, is about 25%. One Loro container per paragraph is therefore expensive to read. Three remedies, best first: read entity properties lazily, when layout first needs a paragraph, instead of all at load (layout of a 500-page document needs only the first pages to show something); store properties in a few flat maps keyed `<id>/<property>` instead of one container per entity, which keeps per-property merging; ask upstream to make the marker check cheaper. The first is a design rule for CORE-101; the second would amend the mapping of spec §16 and should be measured first.

**Applying 1,000 operations.** The miss is a one-time cost of the first update after opening a document. Of its 58 ms, 52% is applying the changes to containers whose state the lazy load had not decoded yet, which decodes them first (44%: mostly the root map of 21,000 paragraph entities, including sorting its keys), and 39% is loading the part of the history that Loro needs to compute version vectors (reading and LZ4-decompressing history blocks of the snapshot) (`results/profile-first-update.txt`). Later updates of the same size take 8.3 ms natively and 12.6 ms in WebAssembly, and one keystroke from another replica 0.03 ms, well within the target. An engine can pay the first cost in the background right after opening, before the first update arrives.

**Undo.** One undo step takes about 0.2 s in the 500-page document (0.26 s in WebAssembly), whatever the size of the step. Loro computes the inverse of a change by checking out the versions around it, and for rich text that rebuilds the story's CRDT state by replaying every operation of the story from the beginning (98% of the time, `replay_container_ops_from_empty`, `results/profile-undo.txt`): about 1.5 million operations for the main story. Undo therefore costs time in proportion to the story's whole history. The remedy is upstream (keep the rebuilt state between undo steps, or rebuild only what follows the change being undone); trimming the history with a shallow snapshot does not help in Loro 1.16.2, it makes undo slower (F11). Until then, an undo in a long document is noticeable but usable.

**Concurrent updates.** A keystroke made on both replicas at once is imported in about 0.2 ms natively and 0.3 ms in WebAssembly. Applying 1,000 edits made while the receiver typed costs 120 ms natively and 170 ms in WebAssembly. 93% of that is one-time work: the first concurrent change to a map makes Loro build its history cache for maps by visiting every change of the document's history (`init_cache_by_visit_all_change_slow`, in which decoding the 640 change blocks is 63%; `results/profile-concurrent-update.txt`). The cache is kept, so the cost is paid once per opened document, in proportion to the history's length.

**Shallow snapshots (F11).** A document opened from the shallow snapshot (old history trimmed) loads and reads as fast as one opened from the full snapshot, but then pays more for almost everything that involves history (`results/native-full-shallow-*.txt` and `native-patched-loro-full-shallow-*.txt`, natively):

| Measurement | Full snapshot, with fix | Shallow snapshot, with fix | Shallow snapshot, without fix |
|---|---|---|---|
| Load and read | 514 ms | 501 ms | 2,613 ms |
| Apply the first 1,000-edit update after opening | 61 ms | 271 ms | 2,306 ms |
| Apply later 1,000-edit updates | 8.2 ms | 8.1 ms | 8.3 ms |
| One undo step | 203 ms | 408 ms | 515 ms |
| One keystroke made on both replicas at once, imported (average of ten) | 0.14 ms | **207 ms** | 207 ms |
| Apply 1,000 edits made while the receiver typed (after eleven such keystrokes) | 113 ms | 558 ms | 559 ms |

The largest cost is the last but one: every keystroke that crosses one of the receiver's own keystrokes takes about 0.2 s to import, three orders of magnitude more than from a full snapshot, so live co-editing of a document opened from a shallow snapshot would lag visibly. Of the first update's 271 ms (with the fix), 86% is seeding Loro's rich-text CRDT state from the trimmed history's starting state, chunk by chunk with a sort (`seed_tracker_from_shallow_root`), which costs more than replaying the full history (`results/profile-shallow-first-update.txt`); without the fix, that starting state also goes through the quadratic decoder of F1. Where a crossing keystroke's 0.2 s goes was not profiled; that every one costs about the same suggests that Loro seeds that state again for each, which the upstream report of F11 should ask.

**A lesson for the engine:** an import into a document that has a subscriber (an undo manager, or the engine's own change listener) makes Loro compute the whole imported state as one change event. Opening the 500-page snapshot with the undo manager already attached took seconds instead of tens of milliseconds before the read (measured during development; not recorded in a result file). The adapter therefore loads first and subscribes afterwards; the engine must do the same.

The final texts differ between the two libraries although their lengths agree, because Automerge marks paragraphs at their start and the BayanDocs model at their end, so the same positions land on different characters; within each library both replicas agree.

### 5.4 Determinism

Views are identical across platforms: `crates/bayan-model/tests/determinism.rs` pins the outcome of a fixed three-replica simulation run (operations applied, refused and skipped, the main story's length and a fingerprint of the final view), and the gate runs it natively and in WebAssembly on Linux, Windows and macOS, so every platform must reach the same committed fingerprint. Snapshot bytes are not identical across platforms: the 10-page document is 185,188 bytes when generated natively and 184,066 bytes when generated in WebAssembly, with the same counts of operations, changes and content (`results/generate-small-native.txt`, `generate-small-wasm.txt`). Loro's encoding depends on how a document reached its state. Nothing in ADR-0005 needs canonical snapshot bytes, but nothing may assume them either: content addressing, deduplication or signatures must hash the view or a canonical export, never a Loro snapshot.

## 6. Answers to spec §18

**Q1. Per-key expansion for dynamically named keys such as `cmt:<id>`?** Yes. Loro resolves a mark key's expansion from the part before its first colon, so the family `cmt` configured with no expansion governs every `cmt:<id>` key, however many comments exist (tested with 200 overlapping comments at every boundary). Two consequences for the spec: Loro refuses (panics on) a configured name that contains a colon, and a key's family is whatever precedes its first colon. The spec's keys must therefore use the colon only as the family separator: `r:b`, `r:rFonts.ascii`, `r:w14.ligatures`, `rev:ins`, not `r.b` or `r.w14:ligatures` (whose family would be `r.w14`, unconfigured).

**Q2. Is the placeholder-plus-mark binding robust under concurrent deletion and re-insertion?** Yes. The binding is a mark `atom` = `"<kind code>:<32 hexadecimal digits>"` with no expansion on exactly one placeholder character. Typing next to an atom never extends the binding; undoing a delete restores every atom with its binding; a cut and paste racing with formatting, deletion, splits and other moves converges in all simulation runs. Formatting operations refuse the `atom` key, so no local edit can remove or forge a binding. Races can leave two atoms bound to the same entity (two replicas move the same object): normalization rule N7 keeps the first in document order. Moving a table into one of its own cells is refused locally, but two concurrent moves (each replica moves one table into a cell of the other) nest the tables in each other. Normalization, which applies N7 in the order it traverses stories, never loops on such a cycle: both tables become unreachable from the main story, so their content is retained but invisible (N5) until an edit or undo reattaches them. That is safe, but surprising for users; CORE-101 should decide whether to reattach orphaned tables automatically. No mark applies to structural atoms (paragraph ends, range delimiters, table blocks): a run-property mark that ends on a paragraph end and expands after would spread into the next paragraph, so the view drops every mark there, and paragraph-mark formatting is stored in the paragraph's properties (`rPr.*`) instead of as marks on the paragraph end, which amends spec §5. A comment highlight whose comment has left the view (only its reference was deleted) is dropped from the view too (N5 for marks).

**Q3. Memory and load time of many small maps (one per paragraph) for a 500-page document in WebAssembly?** 142 MB of linear memory after loading and reading the full model, within the 300 MB target; 0.76 s to load and read with the F1 fix (7.0 s without). The per-entity maps cost 38% of the first read natively (§5.2): acceptable with lazy reading, and replaceable by flat maps if measurements in CORE-101 demand it.

**Q4. Movable lists or a movable tree for table rows and nested structures?** Movable lists suffice. Rows are a movable list per table and cells a movable list per row; concurrent row insertions, deletions and moves merge (a row moved concurrently by two replicas exists once, at the position of one of the moves), and ragged rows are valid. A row that two replicas delete and both undo is stored twice, because each undo inserts it again; N7 shows it once, where it first appears, and the column operations change it once (§2). Nesting is expressed by stories (a cell's story contains a table block atom), not by a tree of containers, so no tree is needed. The one hazard a movable tree would prevent, cycles, comes from moving table atoms; it is handled by refusing local cycles and by a normalization that cannot loop on concurrent ones (Q2). Two safeguards are needed: tables nested deeper than 32 levels are dropped from the view (new rule N9), which bounds the recursion of normalization through nested tables so that hostile documents cannot exhaust the stack; and N7's check that an entity was already reached serves as the visited set that stops cycles.

**Q5. How does undo interact with materialization?** Cleanly, if materialization is not an undo step. When an edit touches structure that only normalization shows (a virtual final paragraph end, a virtual paragraph end before a table found mid-paragraph), the edit first writes that structure with the identifiers and properties the view already shows, commits it with an origin the undo manager ignores, and then performs the edit as its own undo step. Undo then returns the view exactly to the state before the edit, and concurrent materializations by several replicas merge into the same entities, because the identifiers are derived deterministically. The simulation now checks this: every replica compares its view before and after each materialization, and a run fails if one changed it. Entity creation follows the same pattern: Loro 1.16.2 duplicates the content of a child container when redoing its creation (F6), so entities are created outside undo and undo removes only their reference (normalization rule N5 keeps unreferenced entities invisible).

**Q6. Snapshot and update sizes for typical editing sessions?** A single edit sent on its own costs about 105 bytes; a session of 1,000 edits sent as one update about 18.6 KB. The 500-page full model is 9.2 MB with its whole history and 5.4 MB as a shallow snapshot (state with only the latest history), and grows by 48 KB with 1,000 edits. gzip saves only a third; Automerge's snapshot of the subset is five times smaller than Loro's. Replicas should exchange updates, not snapshots. Shallow snapshots are 40% smaller, but in Loro 1.16.2 a document opened from one pays more for its first update (271 ms against 61 ms), its undo steps (408 ms against 203 ms) and, worst, for every concurrent keystroke it imports (207 ms against 0.14 ms) (F11), so the storage and sync work packages must measure that trade-off before choosing the at-rest format.

**Q7. Resource limits needed when importing untrusted updates?** Limits are necessary but far from sufficient. The adapter's `ImportLimits::UPDATE` refuses blobs over 1 MiB, over 100,000 changes or over 2 million operations, refuses snapshots where only updates are expected, and inspects every imported value for nesting deeper than 16 levels. But Loro counts changes and operations only by decoding the whole blob (`LoroDoc::decode_import_blob_meta` decodes every change of an update into a throwaway document), so a hostile blob is fully decoded, twice, before the adapter can refuse it, and that decoding is where the dangers are: Loro panics on crafted updates whose checksum is valid (the checksum is not a signature; anyone can recompute it), requests absurd allocations while decoding some crafted change headers (an allocation failure aborts the process), and overflows the stack on deeply nested values, before the depth inspection can see them. The size limit does not bound the depth: Loro decodes nested values without recursion but frees them recursively, and the metadata call frees its decoded copy before it returns, so a value 21,800 levels deep (a 43,699-byte update) overflows a 2 MiB stack there in a release build, and 6,000 levels (12,097 bytes) do in a debug build; on 8 MiB a release build survives 87,300 levels and aborts at 87,400 (174,899 bytes), a debug build at 23,800 (47,699 bytes); and 1 MiB carries up to 524,238 levels (`results/f5-stack-thresholds.txt`). The depth inspection therefore catches only values shallow enough to survive that first freeing. The adapter contains panics (the replica is poisoned, refuses everything and is never freed) and refuses the deep values it can see; allocation failures and stack overflows need process or worker isolation and upstream fixes (§8.3).

## 8. Security: importing untrusted blobs

### 8.1 How the fuzzer works

`crdt-model fuzz` is a structure-aware mutation fuzzer that needs no third-party code (cargo-fuzz would need libFuzzer, whose NCSA licence is not on the ADR-0017 allowlist; §10). It builds 16 small base documents by random editing, exports their snapshots and the updates two replicas made concurrently after them, and mutates those blobs: bit flips, interesting byte values, inserted, deleted, duplicated and spliced ranges, truncation, rewritten integers and header modes. Nine inputs in ten get a recomputed checksum, so they reach the decoders. Each input is imported, through the adapter, into a freshly loaded copy of its base, with the limits an engine applies to a blob from someone else: `ImportLimits::UPDATE` for updates, and for snapshots the snapshot limits with value inspection on. A successful import must still normalize into a valid view. Workers run on 2 MiB stacks, Rust's default for a new thread and what the engine's thread gets natively (`--stack` changes it), so stack exhaustion is met where the engine would meet it. (The first version's run used 64 MiB stacks and imported snapshots without value inspection; a review pointed out that neither matched an engine.) Panics are recorded with their source location; every input is written to the output folder before it is imported, so even an input that aborts the process is kept (on this machine's disk, that write took about three quarters of a worker's time, so the main run kept its output folder in memory; §8.2). `crdt-model supervise` runs the fuzzer in child processes and restarts a child that aborts; `crdt-model minimize` shrinks a finding by setting changed bytes back to their original value.

### 8.2 Results

### 8.3 What the engine must do

- **Contain panics where the document is known, and at the engine boundary.** `Doc::import` runs Loro's import under `catch_unwind`. On a panic the replica is poisoned: every method of the document, and of every handle to it (stories, maps, lists, registries, undo managers, including handles obtained before the panic), refuses or answers as for an empty document without calling Loro again, whose locks the panic poisoned (F3); and it is never freed, because freeing it can panic again. The host discards it and reloads the last good state without the offending update. This works where panics unwind (native builds). Because a crafted update can also be accepted and panic later, on a read of the data it stored (§8.2), the engine's boundary (the C ABI and the WebAssembly entry points) must catch panics too, as ADR-0006 already requires; such a later panic does not set the poison flag (only `Doc::import` does), so the engine must then discard the replica itself (a follow-up: poison the document on any contained panic). In WebAssembly, Rust panics abort the instance; the engine runs in a Web Worker (ADR-0014), so the web shell must restart the worker and reload, and must not re-import the offending update.
- **Install a content-free panic hook before importing untrusted blobs.** Rust's default panic hook prints a panic's message to standard error before `catch_unwind` takes over, and the messages of Loro and of the crates it uses can quote document text (the containment test's fixture made Loro print the story's text and atom bindings; generic-btree's messages print the tree element, which for rich text holds the text). The adapter does not install a process-wide hook, because the hook belongs to the host; the host must install one that records only that a panic happened, never its message, in logs, crash reports or anything sent to a server (docs AGENTS.md §6). Filtering by crate is not enough, for that reason. bayan-ffi's hook (CORE-007) prints nothing; the containment test (`crates/bayan-crdt/tests/import_panic.rs`) installs one that never prints a message, only where a panic happened.
- **Isolate imports from untrusted peers.** Allocation failures (F4), stack overflows (F5) and the memory that F13's import builds abort the process in every build, and all happen inside Loro's decoding and applying, which the change and operation limits rely on (only the size limit is checked before any decoding): a hostile blob is fully decoded, twice (once by `decode_import_blob_meta` for the limits, once by the import), before the adapter can refuse it, and the size limit neither keeps the nesting depth within the stack (1 MiB carries 524,238 levels) nor the overlap of marks small (51 KB hold 1,000 nested highlights). On the web, the worker is the isolation boundary, with a stack of only 1 MiB by default. On desktop, the engine runs inside the application process, so an abort loses the user's unsaved work. Options, best first: decode and apply untrusted updates first in a separate import process or worker that holds a copy of the document state, with a time and memory budget, and forward them to the main replica only after it succeeded. That copy needs no subscriber, which also makes F13's import fast there (0.34 s for 1,000 nested highlights instead of running out of memory), so the deepest overlap of marks can be measured on it and the update refused above a cap before it reaches a replica with subscribers. Natively, importing on a thread with a much larger stack raises the depth at which freeing overflows (the deepest value that 1 MiB carries needs about 50 MiB in a release build), a partial mitigation for stack overflows worth measuring in the engine work packages; save continuously so that an abort loses nothing; or wait for upstream fixes. `ImportLimits` cannot bound F13 cheaply: the metadata Loro exposes before an import (number of changes, version vectors, timestamps, mode; `loro-internal` `src/encoding.rs:531`) is the same for overlapping and disjoint marks, which cost the same to decode, and counting marks in the adapter's value inspection would be cheap but runs after the expensive import. This is a decision for the engine and sync work packages, recorded here as a follow-up.
- **Changes that wait for a missing dependency are inspected late.** The depth inspection looks at the changes an import applied. A change whose causal predecessors have not arrived yet stays pending (`pending: true`), uninspected, and is inspected only by the import that delivers its dependency and applies it, which then poisons the replica if it is too deep. The sync layer could deliver updates in causal order, or the engine could treat pending blobs from untrusted peers as suspect; a follow-up for the sync work packages.
- **`run-wasi.mjs` is not a sandbox.** It gives the WebAssembly module read and write access to the folder it names, and Node.js documents `node:wasi` as not providing a secure sandbox. It runs the benchmarks; it must never be used to isolate untrusted input.
- **Keep fuzzing.** The fuzzer found the first panic within seconds and the first allocation failure within minutes. Coverage-guided fuzzing (cargo-fuzz) would find more; the owner allowed libFuzzer's licence for fuzzing dependencies that never ship (§10, question 3), so CORE-005 and CORE-006 can use it. The WebAssembly build, whose stack is 1 MiB by default, should be fuzzed too.
- **Limits stay.** Only the size limit is cheap: it is checked before any decoding. The change and operation limits are counted on Loro's full decode of the blob, and the depth limit on the values the import applied. All four refuse what is obviously too big; they are the first fence, not the last.

### 8.4 Platform calls inside Loro (ADR-0012)

ADR-0012 says that the core never calls platform APIs: it asks the host. Loro 1.16.2 makes two such calls of its own, which the first version of this report missed (it mentioned only js-sys's `unsafe-eval` feature):

- **Randomness.** Every `LoroDoc::new()` draws a random peer identifier (`loro-internal` `src/state.rs:467`, through `DefaultRandom`, `src/configure.rs:116-119`), before the adapter replaces it with the peer identifier the host passes; and every import draws one more, because `decode_import_blob_meta` decodes an update into a throwaway `LoroDoc` (`src/encoding/fast_snapshot.rs:573`), so `Doc::import` draws one random number and `Doc::load` two. Natively that is the operating system's generator, through getrandom 0.2. In the browser build (wasm32-unknown-unknown), loro-internal enables getrandom's `js` backend and links wasm-bindgen (a target-specific dependency in its `Cargo.toml`), so the engine module imports `crypto.getRandomValues` (in Node.js, `require("crypto")`).
- **The clock.** The undo manager reads the wall clock on every recorded local change (`src/undo.rs:558`), natively with `SystemTime::now()` and in the browser build with `Date.now()` through wasm-bindgen (`src/change.rs:292-319`). It uses the time only to group changes into undo steps, which the adapter's merge interval switches off (F12). Natively, a clock set before 1970 makes that code panic (it unwraps `duration_since(UNIX_EPOCH)`).

Neither call changes a document's content today, but both are platform calls the core makes behind the host's back, and the browser build's JavaScript must provide them. The options were to ask upstream for a feature that lets the host supply randomness and time, to patch Loro locally, or to amend ADR-0012; the owner chose (question 6) a temporary, documented exception in ADR-0012 (amendment 2026-10-08) for these two calls only, until Loro lets the host supply randomness and time, which the owner asks upstream. The work package that first links bayan-crdt into bayan-engine and bayan-wasm (CORE-007 did not) must check the generated JavaScript imports in `cargo xtask wasm-package`, including that nothing uses `eval` or `new Function`.

## 12. How to reproduce

All commands from the repository root, after `scripts/dev-setup.sh`. The tests, the generated documents, the benchmarks' counts and the convergence runs repeat exactly from their fixed seeds; timings vary with the machine, and a time-bounded fuzzing run stops at a different input each time (each of its rounds repeats exactly from the seed and stream in the log).

```sh
# Tests, including the convergence test at CI size and the normalization property test, natively and in WebAssembly
cargo xtask verify
BAYAN_NORMALIZATION_CASES=100000 cargo test --release --locked -p bayan-model --test normalization -- --nocapture
BAYAN_CONVERGENCE_RUNS=20 BAYAN_CONVERGENCE_OPERATIONS=2000 cargo test --release --locked -p bayan-model --test convergence -- --nocapture

# The synthetic documents and the native benchmarks, in a folder of their own
cargo build --release --locked -p crdt-model
DATA=$(mktemp -d)
target/release/crdt-model generate --mode full --out "$DATA/full-500.bin"      # also writes full-500.bin.shallow
target/release/crdt-model generate --mode subset --out "$DATA/subset-500.bin"
target/release/crdt-model bench --mode full --snapshot "$DATA/full-500.bin"
target/release/crdt-model bench --mode full --snapshot "$DATA/full-500.bin.shallow"
target/release/crdt-model bench --mode subset --snapshot "$DATA/subset-500.bin"

# The same benchmarks in WebAssembly under Node.js 24. run-wasi.mjs shows the module the folder it is given as /data,
# with read and write access, and nothing else; it is not a sandbox (§8.3): give it that folder only, never /tmp or a home folder.
cargo build --release --locked -p crdt-model --target wasm32-wasip1
node spikes/crdt-model/run-wasi.mjs target/wasm32-wasip1/release/crdt-model.wasm "$DATA" bench --mode full --snapshot /data/full-500.bin

# "With fix": a scratch copy of the workspace with loro-f1-fix.patch applied, as results/loro-f1-fix.patch describes

# Profiles of one benchmark phase (profile_first_read, profile_apply, profile_concurrent or profile_undo)
valgrind --tool=callgrind --collect-atstart=no '--toggle-collect=*profile_apply*' target/release/crdt-model bench --mode full --snapshot "$DATA/full-500.bin"

# The full convergence run of the brief (several hours on the 4 cores of the machine above).
# Runs are numbered from the seed (default 0xc0de000400010000), so a run can also be split with --runs and --seed.
target/release/crdt-model converge --runs 1000 --operations 10000 --threads 4
# The confirmation run on the final code: its first 100 runs (about 40 minutes).
target/release/crdt-model converge --runs 100 --operations 10000 --threads 4

# Fuzzing: 75 minutes in child processes that are restarted after an abort, on the engine thread's 2 MiB stacks (--stack);
# --small fuzzes tiny documents. Findings, and every input that aborted the process (<out>/abort-…), are written to the
# output folder, which must stay private (§7).
# Keep the output folder in memory: the fuzzer writes every input there before importing it, which on a disk
# can take most of its time (§8.2).
OUT=$(mktemp -d -p /dev/shm)
target/release/crdt-model supervise --seconds 4500 --workers 2 --out "$OUT"
# Replay or minimize a finding (its file name says which base document it belongs to); --isolated for aborts
target/release/crdt-model replay --input "$OUT/<round>/<finding>"
target/release/crdt-model minimize --input "$OUT/<round>/<finding>" [--isolated]

# The Automerge comparison, natively and in WebAssembly
cargo build --release --locked -p crdt-model-automerge
cargo build --release --locked -p crdt-model-automerge --target wasm32-wasip1
target/release/crdt-model-automerge generate --out "$DATA/am-500.bin"
target/release/crdt-model-automerge bench --snapshot "$DATA/am-500.bin"
node spikes/crdt-model/run-wasi.mjs target/wasm32-wasip1/release/crdt-model-automerge.wasm "$DATA" bench --snapshot /data/am-500.bin
```

The raw output of every measurement in this report is in `spikes/crdt-model/results/` and `spikes/crdt-model-automerge/results/`.
